# LazyInitializationException — "가게 영업시간" 비유

> 주니어에게 `LazyInitializationException` 을 설명할 때 쓰는 칠판용 비유.
> 한 줄 핵심: **"LAZY 데이터를 꺼내려면 가게(트랜잭션)가 열려 있어야 한다."**

---

## 0단계. 그래서 "교환권(프록시)" 안에는 뭐가 들어있나?

3주차에서 `fetch = LAZY` 로 매핑한 연관 필드는 진짜 객체가 아니라 **가짜(프록시)** 가 들어간다고 배웠다. 그 프록시의 정체를 한 번 더 명확하게 보자.

```
🎟️ 교환권 (LAZY 프록시 Dept@123)
┌──────────────────────────┐
│  id      :  5    ← 이것만 들어있음
│  name    :  ❓   ← 비어있음 (아직 DB 안 감)
│  loc     :  ❓   ← 비어있음
└──────────────────────────┘
```

**꼭 기억할 것**

- 교환권은 **`id` 만** 가지고 있다. 실제 데이터(`name`, `loc`...)는 **없다**.
- `dept.getName()` 을 호출하는 그 순간, 교환권이 점원에게 "5번 손님 물건 주세요!" 라고 외친다. 이게 **프록시 초기화**.
- 즉, **`getName()` 한 줄이 사실은 `SELECT` SQL 한 방을 발생시킨다.**

**왜 이런 짓을 하나?** 회원 조회할 때마다 부서·회사·본사까지 다 조인해서 가져오면 낭비다.
**"필요해질 때만 꺼내자"** 가 LAZY 의 철학이다. (대신 그 대가가 이번 주제다.)

---

## 비유 ↔ JPA 개념 매핑

| 비유 | JPA 개념 |
| --- | --- |
| 🏪 가게 영업 | 트랜잭션(`@Transactional`) 살아있음 |
| 👔 점원 | 영속성 컨텍스트 + DB 커넥션 (SQL 날릴 통로) |
| 🚪 셔터 내림 | 트랜잭션 끝 (메서드 리턴 / commit) → 엔티티 **준영속** |
| 🎟️ 교환권 (id만 적혀있음) | **LAZY 프록시** (빈 껍데기) |
| 🛎️ 교환권으로 물건 받기 | **프록시 초기화** (DB 조회 SQL 실행) |

> 한 줄: **교환권은 "물건 받을 권리"일 뿐, 물건 자체가 아니다. 받으려면 점원이 있어야 한다.**

---

## ✅ CASE ① — 영업 중에 물건 받으러 감 → 성공

```
🏪 [ 영업 중 ]   ← 트랜잭션 OPEN, 점원👔 출근 중
┌────────────────────────────────────────┐
│  findById(1L)                          │   회원 받음
│  member.getDept()                      │   교환권🎟️ 받음 (id=5만 있음)
│       .getDeptName()  ─────────────────┼──► 🛎️ "5번 물건 주세요!"
│                                        │         │
│  👔 "여기요~"   ◄───────────────────────┼─────────┘
│  (점원이 DB 에 SELECT 날림)              │
└────────────────────────────────────────┘
                                            👍 진짜 이름 받음 (초기화 성공)
```

영업 중이라 **점원이 있다.** 교환권을 SQL 로 바꿔 물건을 가져올 수 있다.
= 영속 상태에서는 프록시가 영속성 컨텍스트를 통해 DB 조회에 성공한다.

---

## 💥 CASE ② — 셔터 내린 뒤 물건 받으러 감 → LazyInitializationException

```
🏪 [ 영업 중 ]   ← 트랜잭션 OPEN
┌────────────────────────────────────────┐
│  findById(1L)                          │   회원 + 교환권🎟️ 만 받고
│  (getDeptName 안 부름)                  │   실제 물건은 안 받음
└────────────────────────────────────────┘
            │
            ▼
🚪 [ 셔터 내림 ]  ← 트랜잭션 끝! 점원👔 퇴근. member = 준영속
┌────────────────────────────────────────┐
│  member.getDept()                      │
│       .getDeptName()  ─────────────────┼──► 🛎️ "5번 물건 주세요!"
│                                        │         │
│  ❌ 아무도 없음   ◄──────────────────────┼─────────┘
│  (SQL 날릴 통로가 사라짐)                 │
└────────────────────────────────────────┘
                                            💥 "no Session" → 예외!
```

`findById` 직후 안 꺼내고, **셔터 내린 뒤에** 꺼내려 한 게 죄다.
교환권은 종잇조각일 뿐 — 점원(영속성 컨텍스트)이 없으면 SQL 을 못 날린다 → 예외.

---

## 두 케이스의 차이는 단 하나

```
 영업중 ─────────────────── 셔터내림 ───────────────►  시간
   │                          │
findById                      │
교환권🎟️ 받음                   │
   │                          │
   ├─ ✅ 여기서 getDeptName() → 점원 있음, 성공
   │                          │
   │                          └─ 💥 여기서 getDeptName() → 점원 없음, 예외
```

**코드는 똑같다** — `getDept().getDeptName()`.
**차이는 "셔터 내리기 전이냐 후냐" 단 하나.**

## 실무에서 가장 흔한 패턴 — Service → Controller

LazyInitializationException 의 90% 는 이 구조에서 나온다.
**서비스가 엔티티를 그대로 반환하고, 컨트롤러/뷰에서 LAZY 필드를 건드리는** 패턴이다.

```java
@Service
public class MemberService {

    @Transactional
    public Member findMember(Long id) {
        return memberRepository.findById(id).orElseThrow();
    }   // 🚪 메서드 리턴 = 셔터 내림. 여기서 member 는 준영속.
}

@RestController
public class MemberController {

    public String getMemberDept(Long id) {
        Member m = memberService.findMember(id);   // 트랜잭션 밖
        return m.getDept().getName();              // 💥 셔터 내린 후 교환권 사용
    }
}
```

**진단 체크리스트**

1. 예외가 터진 줄에 LAZY 필드 접근이 있나? (`.getDept()`, `.getOrders()` 등)
2. 그 줄이 `@Transactional` **밖**인가? (컨트롤러 또는 트랜잭션 끝난 후)
3. 둘 다 yes → 그게 원인이다.

---

## 칠판에서 말로 짚을 포인트

- **두 케이스의 코드는 똑같다.** 다른 건 단 하나 — **"셔터 내리기 전이냐, 후냐"**. 손으로 가리키며 강조.
- CASE ② 의 죄: `findById` 직후 안 꺼내고 **셔터 내린 뒤** 꺼낸 것. → "영업 중에 미리 받아뒀어야지!"
- 예외 메시지 `could not initialize proxy ... no Session` 의 **`no Session`** ↔ 그림의 **"❌ 아무도 없음"**. → 메시지가 곧 답이다.

## 자주 나오는 질문

### Q1. "저는 평소에 안 터지던데요?"

스프링 부트가 기본으로 **영업시간을 응답 끝까지 늘려주는 옵션** 을 켜둬서 평소엔 가려진다.

```yaml
# application.yml
spring:
  jpa:
    open-in-view: true   # 기본값 — 응답이 클라에 나갈 때까지 가게 영업 유지
```

이 옵션을 **OSIV** (Open Session In View) 라고 부르며, View(컨트롤러/JSON 직렬화) 단계까지 영속성 컨텍스트를 열어둔다.
실무에선 성능·트랜잭션 관리 이슈로 **끄는 경우가 많고, 끄는 순간 터진다.** → **가려진 거지 해결된 게 아니다.**

(OSIV 의 단점·내부 동작은 별도 주차에서. 지금은 "그래서 평소엔 안 터지더라" 정도만.)

### Q2. "교환권 말고 그냥 진짜 객체를 주면 안 되나요?"

된다 — `fetch = EAGER` 로 바꾸면 회원 조회 시 부서까지 **한 번에 조인해서** 가져온다. 다만:

- 한 부서를 보려고 **모든 회원 조회마다** 조인을 부담해야 함
- 연관관계가 깊어지면 (`Member → Dept → Company → ...`) 한 번 조회에 테이블 5~6 개가 같이 끌려옴
- 그래서 **JPA 의 권장은 전부 LAZY**, 필요한 경우만 fetch join 으로 같이 가져오는 것

→ 이어지는 떡밥, 다음 주에.

## 해결 방향 — 맛보기 (다음 주 떡밥)

```java
// 방법 ①: 영업 중에 미리 꺼내두기 (이번 주 범위)
@Transactional
public String getDeptName(Long id) {
    Member m = memberRepository.findById(id).orElseThrow();
    return m.getDept().getDeptName();   // 트랜잭션 안에서 미리 꺼냄
}
```

> "근데 매번 이렇게 미리 꺼내는 거 귀찮죠? 그래서 **'조회할 때 아예 같이 가져오는 법(Fetch Join)'** 을 다음 시간에 배웁니다."

## 참여형 마무리 퀴즈

> 이 코드, 어디서 터질까요? 손가락으로 줄을 짚어보세요.
>
> ```java
> Member m = service.findMember(1L);   // (A)
> m.getDept().getDeptName();           // (B)
> ```
>
> **정답: B.**
> **이유: A 에서 가게 셔터가 내려갔다(`@Transactional` 끝). 그 후의 LAZY 접근은 모두 💥.**
