# LazyInitializationException — "가게 영업시간" 비유

> 주니어에게 `LazyInitializationException`을 설명할 때 쓰는 칠판용 비유.
> 핵심은 **두 케이스의 코드가 똑같다는 것** — 차이는 "셔터 내리기 전이냐, 후냐" 단 하나다.

---

## 비유 ↔ JPA 매핑

| 비유 | JPA 개념 |
| --- | --- |
| 🏪 가게 영업 | 트랜잭션(`@Transactional`) 살아있음 |
| 🚪 셔터 내림 | 트랜잭션 끝 (메서드 리턴 / commit) → 엔티티 **준영속** |
| 🎟️ "나중에 살게요" 교환권 | **LAZY 프록시** (빈 껍데기) |
| 🛎️ 교환권으로 물건 받기 | **프록시 초기화** (DB에서 진짜 데이터 가져오기) |

> 한 문장 요약: **"LAZY 데이터는 트랜잭션이 살아있을 때만 꺼낼 수 있다."**

---

## ✅ CASE ① — 영업 중에 물건을 받으러 감 → 성공

```
        🏪 [ 영업 중 ]   ← 트랜잭션 OPEN
        ┌──────────────────────────┐
        │  findById(1L)            │   회원 받음
        │  member.getDept()        │   교환권(프록시) 받음
        │       .getDeptName()  ───┼──► 🛎️ "그거 주세요!"
        │                          │         │
        │   점원: "여기요~" ◄───────┼─────────┘  DB 조회 OK
        └──────────────────────────┘
                                       👍 값 받음 (초기화 성공)
```

영업 중(트랜잭션 안)이라 점원이 있어서, 교환권을 내밀면 물건을 받을 수 있다.
= 영속 상태에서는 프록시가 DB에 SQL을 날려 초기화에 성공한다.

---

## 💥 CASE ② — 셔터 내린 뒤 물건을 받으러 감 → LazyInitializationException

```
        🏪 [ 영업 중 ]   ← 트랜잭션 OPEN
        ┌──────────────────────────┐
        │  findById(1L)            │   회원 + 교환권만 받고
        │  (getDeptName 안 부름)    │   아직 물건은 안 받음
        └──────────────────────────┘
                   │
                   ▼
        🚪 [ 셔터 내림 ]  ← 트랜잭션 끝! (member = 준영속)
        ┌──────────────────────────┐
        │  member.getDept()        │
        │       .getDeptName()  ───┼──► 🛎️ "그거 주세요!"
        │                          │         │
        │   ❌ 아무도 없음 ◄────────┼─────────┘  DB 조회할 통로 없음
        └──────────────────────────┘
                                       💥 "no Session" → 예외!
```

`findById` 직후에 안 꺼내고, **셔터 내린 뒤(트랜잭션 끝난 뒤)** 꺼내려 한 게 문제다.
점원이 없으니(살아있는 영속성 컨텍스트가 없으니) 교환권은 종잇조각일 뿐 → 예외.

---

## 한 컷(타임라인) 버전 — 칠판 공간이 좁을 때

```
 영업중 ───────────────── 셔터내림 ───────────────►  시간
   │                        │
findById                    │
교환권(프록시)받음            │
   │                        │
   ├─ 여기서 getDeptName() ─→ ✅ OK
   │                        │
   │                        └─ 여기서 getDeptName() → 💥 예외
```

---

## 칠판에서 말로 짚을 포인트

- **두 케이스의 코드는 똑같다** (`getDept().getDeptName()`). 다른 건 단 하나 — **"셔터 내리기 전이냐, 후냐"**. 손으로 가리키며 강조.
- CASE ②의 죄: `findById` 다음 바로 안 꺼내고 **셔터 내린 뒤에 꺼낸 것**. → "영업 중에 미리 받아뒀어야지!"
- 예외 메시지 `could not initialize proxy ... no Session` 의 **`no Session`** ↔ 그림의 **"❌ 아무도 없음"** 을 연결. → 메시지가 곧 답이다.

---

## 자주 나오는 질문 — "저는 평소에 안 터지던데요?"

> 스프링 부트가 기본으로 **영업시간을 응답 끝까지 늘려주는 옵션(OSIV, `spring.jpa.open-in-view=true`)** 을 켜둬서 평소엔 가려진다.
> 실무에선 성능 때문에 끄는 경우가 많고, **끄는 순간 터진다.** → **가려진 거지 해결된 게 아니다.**

(OSIV 내부 동작은 이 단계에서 생략 — 주제가 흐려진다.)

---

## 해결은 "맛보기"만 (다음 떡밥)

```java
// 영업 중에 미리 꺼내두면 됨 (이번 시간 범위)
String name = member.getDept().getDeptName();  // 트랜잭션 안에서
```

> "매번 이렇게 미리 꺼내는 거 귀찮죠? 그래서 '조회할 때 아예 같이 가져오는 법(**Fetch Join**)'을 다음에 배웁니다."

## 참여형 마무리 퀴즈

> 이 코드, 어디서 터질까요? 손가락으로 줄을 짚어보세요.
>
> ```java
> Member m = service.findMember(1L);   // (A)
> m.getDept().getDeptName();           // (B)
> ```
>
> 정답: **B**. 왜? **A에서 가게 셔터가 내려갔으니까(트랜잭션 끝).**
