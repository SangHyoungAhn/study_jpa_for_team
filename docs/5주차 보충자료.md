## 목표

> [!Important]
> 5주차 본편(1·2·3단계)은 **`N:1`(예: `Member → Department`)** 까지만 다뤘다.
> `N:1` 에서는 **Fetch Join 한 방이면 끝**이라 함정이 없었기 때문이다.
> 이 보충자료는 **`1:N` 컬렉션(예: `Post → List<Comment>`)** 으로 넘어가는 순간 생기는 문제들을 "왜?" 로 답할 수 있게 한다.
>
> - 왜 부모를 저장·삭제하면 자식도 따라가는가? (혹은 왜 안 따라가는가?) — *1단계*
> - 왜 컬렉션 Fetch Join 에 페이징을 걸면 위험한가? — *2단계*
> - 그럼 컬렉션은 대체 어떻게 페이징하나? — *3단계 (batch fetch size)*

> [!Note]
> **본편과의 경계는 단계 번호가 아니라 `N:1` / `1:N` 다.**
> `N:1`(다대일, FK 가진 쪽이 단건 참조)은 함정이 없어 본편에서 완결했고,
> `1:N`(일대다, 컬렉션)은 중복 row·페이징·삭제 전파 같은 문제가 줄줄이 따라오므로 여기서 본다.
> (DTO 프로젝션·OSIV·전체 선택 기준은 **6주차**에서 조회 전략으로 따로 다룬다.)

## 0단계. 어디서 이어지나 — N:1 까지는 본편에서 끝냈다

본편에서 확인한 것:

- 연관관계 매핑(양방향·연관관계 주인·mappedBy·편의 메서드)
- N+1 문제를 `show-sql` 로 눈으로 확인
- `N:1` 에서 **Fetch Join** 으로 N+1 → 쿼리 1번

`Member → Department` 처럼 **단건(`N:1`)** 을 당겨올 때는 여기서 이야기가 끝난다. 조인해도 행이 늘지 않고, 페이징도 정상 동작한다.

문제는 방향이 반대인 **`1:N` 컬렉션**(`Department → List<Member>`, 게시판 `Post → List<Comment>`)이다.
"부서 하나에 회원 여럿", "게시글 하나에 댓글 여럿" 을 당겨오는 순간, 행이 뻥튀기되고 페이징이 깨진다. 그 전에, 양방향 부모-자식을 만들었으니 **저장·삭제가 어디까지 전파되는지**부터 정리한다.

---

## 1단계. 영속성 전이 — cascade 와 orphanRemoval

게시판으로 보면 `Post` 와 `Comment` 는 **생명주기가 거의 붙어 있다.** 게시글을 지우면 그 댓글들도 의미가 없다.
이때 **"부모에 한 작업이 자식에게도 전파되느냐"** 를 정하는 게 `cascade` 와 `orphanRemoval` 이다.

```java
@Entity
public class Post {

    @OneToMany(mappedBy = "post",
               cascade = CascadeType.ALL,   // 부모의 persist/remove 등을 자식에게 전이
               orphanRemoval = true)        // 컬렉션에서 빠진 자식을 DELETE
    private List<Comment> comments = new ArrayList<>();
}
```

### cascade — "부모에 한 일을 자식에게도"

`cascade` 는 **영속성 전이**다. 부모 엔티티에 일어난 영속성 작업을 자식에게도 함께 적용한다.

```java
Post post = new Post("제목");
post.addComment(new Comment("첫 댓글"));   // 편의 메서드로 양쪽 세팅
post.addComment(new Comment("둘째 댓글"));

postRepository.save(post);   // cascade = PERSIST 덕에 Comment 들도 함께 INSERT
                             // (cascade 없으면 Comment 는 저장 안 됨 → 따로 save 해야)
```

| 종류 | 의미 |
| --- | --- |
| `PERSIST` | 부모 저장 시 자식도 저장 |
| `REMOVE` | 부모 삭제 시 자식도 삭제 |
| `ALL` | 위 전부 (MERGE/REFRESH/DETACH 포함) |

### orphanRemoval — "관계가 끊어지면 자식을 삭제"

`orphanRemoval = true` 는 **부모의 컬렉션에서 자식이 빠지는 순간**(고아가 되는 순간) 그 자식을 DELETE 한다.

```java
post.getComments().remove(comment);   // 컬렉션에서 제거 → orphanRemoval 이 DELETE 실행
```

### 둘의 차이 — 헷갈리기 쉬운 지점

| | 트리거 | 예 |
| --- | --- | --- |
| `cascade = REMOVE` | **부모 자체가 삭제될 때** | `postRepository.delete(post)` → 댓글 전부 삭제 |
| `orphanRemoval = true` | **부모는 살아있고, 관계만 끊길 때** | `post.getComments().remove(c)` → 그 댓글만 삭제 |

> **핵심:** 부모가 죽을 때만 같이 죽이면 `cascade.REMOVE`, 부모에서 떼어내기만 해도 죽여야 하면 `orphanRemoval`. 게시글-댓글처럼 자식이 **그 부모에게만 종속**되면 보통 `CascadeType.ALL + orphanRemoval = true` 를 함께 쓴다.

> [!Caution]
> **공유되는 엔티티에는 cascade/orphanRemoval 을 쓰면 안 된다.**
> 자식이 여러 부모(또는 다른 곳)에서 참조되는 엔티티라면, 부모 하나를 지웠다고 자식까지 지워지면 **다른 쪽 데이터가 함께 날아간다.**
> 이 옵션은 **"부모-자식 생명주기가 완전히 일치하고, 자식을 그 부모만 소유한다"** 가 확실할 때만 켠다. (게시글-댓글이 전형적인 그 경우)
> 잘못 켜면 "게시글 하나 지웠는데 엉뚱한 데이터가 대량으로 삭제" 되는, 추적하기 어려운 운영 사고로 이어진다.

## 2단계. 컬렉션 Fetch Join 의 함정 세 가지

`N:1` 에선 안 보이던 문제가 `1:N` Fetch Join 에서 한꺼번에 나타난다.

```java
@Query("SELECT p FROM Post p JOIN FETCH p.comments")
List<Post> findAllWithComments();
```

### ① 중복 row — DISTINCT 가 필요하다

`1:N` 조인은 **자식 수만큼 부모 행이 복제**된다. 게시글에 댓글이 3개면, 그 게시글 행이 3번 나온다.

```sql
-- Post 1개 + Comment 3개 → 결과 row 3개 (Post 가 3번 중복)
```

```java
@Query("SELECT DISTINCT p FROM Post p JOIN FETCH p.comments")  // DISTINCT 로 부모 중복 제거
List<Post> findAllWithComments();
```

> Hibernate 6 부터는 엔티티 조회 시 중복을 자동으로 걸러주지만, **의미를 드러내기 위해 `DISTINCT` 를 적는 습관**을 들이는 게 좋다.

### ② 페이징 — 컬렉션 Fetch Join + 페이징은 위험하다

이게 본편을 `N:1` 로 끊은 진짜 이유다.

```java
// ❌ 컬렉션 fetch join 에 페이징을 걸면…
@Query("SELECT DISTINCT p FROM Post p JOIN FETCH p.comments")
Page<Post> findAll(Pageable pageable);
```

행이 뻥튀기된 상태라 DB 레벨에서 "게시글 10개" 를 페이징할 수 없다. 그래서 Hibernate 는 경고 로그를 남기고 **전체를 메모리로 올린 뒤 메모리에서 페이징**한다.

```
firstResult/maxResults specified with collection fetch; applying in memory!
```

데이터가 많으면 그대로 `OutOfMemoryError` 위험. **컬렉션 Fetch Join 에는 페이징을 걸지 않는다.** (해결책은 3단계)

### ③ 컬렉션은 하나만 — 둘 이상 Fetch Join 금지

```java
// ❌ comments 와 likes, 컬렉션 둘을 동시에 fetch join
@Query("SELECT p FROM Post p JOIN FETCH p.comments JOIN FETCH p.likes")
```

컬렉션 둘을 조인하면 **카테시안 곱**(댓글 3 × 좋아요 4 = 12행)이 되어 데이터가 폭발하고, Hibernate 는 `MultipleBagFetchException` 을 던진다.
**한 쿼리에서 Fetch Join 하는 컬렉션은 하나까지.** 나머지는 batch size(3단계)로 푼다.

## 3단계. Batch Fetch Size — 컬렉션 페이징의 정답

2단계에서 "컬렉션은 페이징을 못 건다" 고 했다. 그럼 게시글 목록 + 각 댓글을 페이징하려면?
**컬렉션은 LAZY 로 두고, 페이징은 부모(루트)에만 건다.** 그리고 자식 컬렉션은 **batch fetch** 로 묶어서 가져온다.

```yaml
# application.yml — 전역 설정 (권장)
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

또는 개별 컬렉션/엔티티에:

```java
@BatchSize(size = 100)
@OneToMany(mappedBy = "post")
private List<Comment> comments = new ArrayList<>();
```

### 원리 — N 번 단건 조회를 IN 으로 묶는다

batch size 가 없으면, 게시글 10개의 댓글을 꺼낼 때 **게시글마다 한 번씩** 댓글 쿼리가 나간다(= N+1).

```sql
SELECT * FROM comment WHERE post_id = 1;   -- 10번 반복
SELECT * FROM comment WHERE post_id = 2;
...
```

batch size 를 켜면, LAZY 컬렉션을 처음 건드리는 순간 **묶어서 IN 쿼리 한 방**으로 가져온다.

```sql
SELECT * FROM comment WHERE post_id IN (1, 2, 3, ..., 10);   -- 한 번에
```

> **쿼리 수:** `1 + N` → `1 + ⌈N / batch_size⌉`.
> batch size 가 부모 개수보다 크면 사실상 **쿼리 2번**(부모 1 + 자식 1)으로 끝난다.

### Fetch Join vs Batch Size — 역할이 다르다

| | 쓰는 곳 | 페이징 |
| --- | --- | --- |
| **Fetch Join** | 단건/소수의 연관을 확실히 한 방에 | 컬렉션이면 ❌ |
| **Batch Size** | 컬렉션을, 특히 **페이징과 함께** | ✅ (루트만 페이징) |

> **정리:** "컬렉션 + 페이징" 이라는 조합을 만나면 Fetch Join 이 아니라 **batch fetch size** 가 정답이다.
> 실무에서는 `default_batch_fetch_size` 를 **전역으로 켜 두는 것** 을 기본값처럼 권장한다(100~1000). 의도치 않은 N+1 을 전반적으로 완화해 준다.

---

## 한 줄 요약

> `N:1` 은 Fetch Join 한 방으로 끝나지만(본편), **`1:N` 컬렉션은 함정이 줄줄이 따라온다.**
> 부모-자식 생명주기는 **`cascade`/`orphanRemoval`** 로,
> 컬렉션 Fetch Join 의 **중복 row 는 `DISTINCT`**, **페이징은 `batch fetch size`**, **둘 이상 컬렉션은 금지** 로 푼다.
> (DTO·OSIV 같은 조회 전략은 6주차에서 이어진다.)
