# 1차 캐시와 영속성 컨텍스트

`MemberRepositoryTest`의 `findById_Cache` / `findById_Cache_Outside` 테스트를 만들면서
정리한 내용입니다.

---

## 1. "같은 객체"란 정확히 무슨 뜻인가

> 궁금증: 영속성 컨텍스트 때문에 "같은 객체"라고 하는데, 객체의 주소는 다른 거 아닌가?

`==`(즉 `isSameAs`)는 **두 변수가 메모리에서 같은 인스턴스(=같은 주소)를 가리키는가**를 봅니다.

`findById_Cache`에서 `member1 == member2`가 `true`라는 건 —
**주소가 다른 두 객체가 우연히 같은 게 아니라, 애초에 주소가 똑같은 하나의 객체**라는 뜻입니다.
변수 이름만 둘(`member1`, `member2`)이지 실제 메모리상 객체는 **딱 하나**입니다.

```
[상자(영속성 컨텍스트)]
        Member@1a2b   ← 메모리에 객체는 하나뿐
        ↑        ↑
   member1    member2   ← 변수 둘이 같은 주소를 가리킴
```

> 즉 "주소가 다른데 같다고 해도 되나?"가 아니라, **1차 캐시 케이스에선 주소 자체가 같습니다.**
> 이게 1차 캐시의 정체입니다: 같은 행을 두 번 조회해도 **새 객체를 안 만들고**,
> 상자에 보관해둔 그 인스턴스의 **주소를 그대로 다시 돌려줍니다.**

반대로 `findById_Cache_Outside`는 중간에 `clear()`로 상자를 비워서, 두 번째 조회 때
**새 객체를 새 주소에 만들어** 돌려줍니다. → 주소가 다름 → `==` `false`.

### 설명할 때 이렇게 말하면 깔끔하다

> "1차 캐시는 **같은 데이터를 두 번 조회해도 객체를 새로 만들지 않고, 영속성 컨텍스트에 보관된
> 같은 인스턴스(같은 주소)를 그대로 돌려준다.** 그래서 `==` 비교가 `true`다.
> 반대로 영속성 컨텍스트가 바뀌면(`clear`) 보관해둔 게 사라져서 새 인스턴스(다른 주소)를
> 만들어 돌려주니 `==`가 `false`가 된다."

### "주소"를 눈으로 보여주기

말로만 "주소가 같다/다르다"는 추상적이라, `System.identityHashCode()`로 주소에 대응하는 값을
직접 출력하면 효과적입니다.

```java
// findById_Cache
System.out.println("member1 주소: " + System.identityHashCode(member1));
System.out.println("member2 주소: " + System.identityHashCode(member2));
// → 두 값이 똑같이 찍힘 (같은 객체)
```

```java
// findById_Cache_Outside
System.out.println("m1 주소: " + System.identityHashCode(m1));
System.out.println("m2 주소: " + System.identityHashCode(m2));
// → 두 값이 다르게 찍힘 (다른 객체)
Assertions.assertThat(m1).isNotSameAs(m2);                // 주소 다름
Assertions.assertThat(m1.getId()).isEqualTo(m2.getId());  // 그래도 같은 DB 행
```

> ⚠️ `System.identityHashCode`의 값을 "진짜 메모리 주소"라고 단정하지는 말 것.
> 정확히는 **JVM이 각 객체에 부여하는 고유 신원 값**이고, 보통 주소 기반으로 만들어지지만
> GC가 객체를 옮겨도 값은 유지됩니다. 가르칠 때는 **"객체를 구분하는 고유 번호(주소 같은 것)"**
> 정도로 말하면 정확하면서도 직관적입니다.

### 정리

| | 두 번째 조회 결과 | `==` (`isSameAs`) | identityHashCode |
|---|---|:---:|---|
| `findById_Cache` | 상자에 보관된 **같은 인스턴스** | `true` | 두 값 동일 |
| `findById_Cache_Outside` | `clear` 후 **새로 만든 인스턴스** | `false` | 두 값 다름 |

## 2. 테스트라서 매번 데이터가 사라지는 이유 (drop? 롤백?)

> 궁금증: 테스트라서 다시 drop table 하는 건가?

"drop"이 일어나는 메커니즘이 **두 가지**라 구분해야 합니다.

### ① 매 테스트마다 → `@Transactional` 롤백 (drop이 아님)

`@DataJpaTest`에는 `@Transactional`이 **자동으로** 붙어 있습니다.

```
테스트 시작 → 트랜잭션 시작
  insert dept, insert member, select ...
테스트 끝 → 트랜잭션 롤백(rollback)  ← commit이 아니라 되돌림!
```

테이블을 drop 하는 게 아니라, **이번 테스트에서 넣은 데이터(INSERT)를 통째로 취소**합니다.
그래서 다음 테스트는 깨끗한 상태에서 시작합니다.

> 세 테스트가 전부 똑같이 `"D011" 비즈테크팀`을 insert 하는데도 **중복 키 에러가 안 나는 이유**가
> 바로 이 롤백입니다. 매번 되돌리니 각 테스트가 독립적으로 돕니다.

### ② 테스트 전체 실행 시작/끝 → `create-drop` (진짜 drop table)

테이블 구조 자체는 `ddl-auto`가 관리합니다. `@DataJpaTest`는 기본적으로 **임베디드 H2(메모리 DB)**를
쓰고, 보통 `ddl-auto: create-drop`으로 동작합니다.

```
테스트 클래스 실행 시작 → create table member ..., create table department ...
  (테스트들 다 돌고)
JVM/컨텍스트 종료 → drop table member, drop table department  ← 진짜 drop
```

이건 매 테스트마다가 아니라 **테스트 실행 전체 단위로 한 번씩** 일어납니다.

### 정리

| 단위 | 무슨 일 | 메커니즘 |
|------|---------|----------|
| 테스트 메서드마다 | INSERT한 데이터 취소 | `@Transactional` **롤백** (drop 아님) |
| 테스트 실행 전체 | 테이블 만들고 없애기 | `ddl-auto: create-drop` |

> 로그에서 `drop table`을 봤다면 그건 ②번(전체 종료 시점)이고,
> 테스트마다 데이터가 사라지는 건 ①번(롤백)입니다.
> 테스트 사이엔 `drop`이 아니라 `rollback`만 보입니다.

## 3. 1차 캐시로 얻는 이점

### ① 반복 조회 시 DB 쿼리 절감 (성능)

같은 트랜잭션 안에서 같은 엔티티를 여러 번 조회해도 SELECT는 **딱 한 번**만 나갑니다.

```java
Member m1 = memberRepository.findById(1L).get();  // SELECT 발생
Member m2 = memberRepository.findById(1L).get();  // DB 안 감, 캐시에서
```

> 한 비즈니스 로직 안에서 같은 엔티티를 여러 메서드가 각자 조회하는 일이 흔한데,
> 그때마다 DB를 때리는 낭비를 1차 캐시가 자동으로 막아줍니다.

### ② 객체 동일성(identity) 보장

같은 트랜잭션에서 같은 행을 조회하면 **항상 같은 인스턴스**가 보장됩니다(`==` true).

```java
Member m1 = repo.findById(1L).get();
Member m2 = repo.findById(1L).get();
m1.setName("변경");
// m2.getName() 도 "변경" — 같은 객체니까
```

> 한 곳에서 수정한 내용이 다른 곳에서 조회한 객체에도 자동 반영됩니다.
> "같은 데이터인데 객체가 둘이라 한쪽만 바뀌는" 버그가 원천 차단됩니다.

### ③ 변경 감지(Dirty Checking)의 기반 — 실무적으로 가장 큰 이점

1차 캐시에 엔티티를 보관할 때 **처음 상태의 스냅샷**도 같이 저장합니다.
트랜잭션이 끝날 때 현재 값과 스냅샷을 비교해, 바뀐 게 있으면 **자동으로 UPDATE**를 날립니다.

```java
Member m = repo.findById(1L).get();
m.setName("새이름");
// repo.save(m) 안 해도 → 트랜잭션 끝날 때 UPDATE 자동 실행!
```

> `update` SQL을 직접 안 짜도 됩니다. 객체 값만 바꾸면 JPA가 알아서 DB에 반영합니다.
> 1차 캐시(+스냅샷)가 없으면 불가능한 기능입니다.

### ④ 쓰기 지연(Write-Behind)

INSERT/UPDATE를 즉시 DB에 보내지 않고 **쓰기 지연 SQL 저장소**에 쌓아뒀다가,
`flush` 시점에 모아서 한 번에 보냅니다.

> 매번 DB와 통신하지 않고 모아서 보내니 네트워크 왕복이 줄고,
> JDBC batch와 결합하면 대량 처리 성능이 좋아집니다.

### 정리 표

| 이점 | 한 줄 요약 | 테스트에서 본 흔적 |
|------|-----------|-------------------|
| 쿼리 절감 | 같은 조회 두 번 → SELECT 한 번 | `findById` 2회, SELECT 1회 |
| 동일성 보장 | 같은 행 = 같은 인스턴스(`==`) | `isSameAs` true |
| 변경 감지 | `save` 없이 값만 바꿔도 UPDATE | (다음에 테스트해볼 만함) |
| 쓰기 지연 | SQL 모았다 `flush`에 한 번에 | `em.flush()` 명시 호출 |

### 주의 (균형 잡힌 시각)

- 1차 캐시는 **하나의 트랜잭션(영속성 컨텍스트) 범위 안에서만** 유효합니다.
  트랜잭션이 끝나면 사라지므로, 여러 요청에 걸친 캐싱(2차 캐시·Redis 등 외부 캐시)과는 다릅니다.
- 범위가 좁아 메모리 부담은 적지만, **한 트랜잭션에서 수만 건을 조회하면 1차 캐시에 다 쌓여**
  메모리를 먹을 수 있습니다. 대량 배치에선 중간중간 `em.clear()`로 비워주기도 합니다.
