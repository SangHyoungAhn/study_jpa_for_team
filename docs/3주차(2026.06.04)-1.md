## 1단계. 왜 JPA를 쓰는가 (진화론)

JPA를 쓰는 이유는 **"JPA가 없던 시절에 뭐가 불편했는지"** 를 보면 와닿는다.

### JPA 이전 — JDBC / MyBatis의 불편함

```java
// SQL을 하나하나 다 적어줘야 한다 (JDBC)
String sql = "INSERT INTO member(name, age, email) VALUES(?, ?, ?)";
pstmt.setString(1, member.getName());
        pstmt.setInt(2, member.getAge());
        pstmt.setString(3, member.getEmail());
```

```java
//DAO, Mapper, xml 생성 (MyBatis)
@Mapper
public interface MemberMapper {
    void save(Member member);
    void update(Member member);
}

<mapper namespace="excodeMyBatis.mapper.MemberMapper">
    <insert id="save" parameterType="excodeMyBatis.model.Member">
INSERT INTO MEMBER(NAME, AGE, ADDRESS)
VALUES (#{name}, #{age}, #{address})
    </insert>

    <update id="update" parameterType="excodeMyBatis.model.Member">
UPDATE MEMBER
SET NAME = #{name},
AGE  = #{age},
ADDRESS = #{address}
WHERE ID = #{id}
    </update>
</mapper>
```
**불편함** 세 가지:

- **반복되는 CRUD SQL** — 테이블마다 `insert/select/update/delete`를 일일이 적는다.
- **컬럼 하나 추가 = 전부 수정** — `Member`에 `phone`이 추가되면 관련 SQL·매핑을 전부 찾아 고쳐야 한다.
- **패러다임 불일치** — 자바는 객체(참조)로, DB는 테이블(외래키)로 생각한다. 이 간극을 개발자가 매번 손으로 메꾼다. ← **가장 핵심**

---
### JPA의 해법 — "객체답게" 다루기


**(1) 패러다임 불일치 해결 — 연관관계**
```java
// JDBC 사고: team_id(FK)를 따로 들고 다니며 team을 또 조회
Long teamId = member.getTeamId();

// JPA 사고: 그냥 객체 참조
Team team = member.getTeam();          // 객체 그래프를 자연스럽게 탐색
team.getName();
```

**(2) SQL을 직접 안 짜도 됨 — 생산성**
```java
em.persist(member);                    // 이 한 줄이 INSERT SQL을 자동 생성
// 컬럼이 추가돼도 엔티티 필드만 추가하면 됨 → SQL 수정 없음
```

**(3) 1차 캐시 / 영속성 컨텍스트 — 성능 + 일관성**
```java
Member m1 = em.find(Member.class, 1L); // DB 조회
Member m2 = em.find(Member.class, 1L); // DB 안 감 (1차 캐시에서 반환)
m1 == m2;                              // true — 같은 객체 보장
```

**(4) 변경 감지 (Dirty Checking) — UPDATE가 사라짐**
```java
Member member = em.find(Member.class, 1L);
member.setName("새이름");              // update 코드를 안 적었는데
// 트랜잭션이 끝나면 JPA가 알아서 UPDATE SQL 실행
```
**(3),(4)에 관한 내용은 향후, 진행하면서 설명**

## 환경 구축 — H2 (눈으로 보는 DB)

H2는 가볍고, **웹 콘솔로 테이블/데이터를 눈으로 볼 수 있는** DB다.
아래 설정처럼 `tcp://localhost/~/studyjpa` 를 쓰면 **홈 디렉터리에 파일로 저장되는
파일 기반 DB(서버 모드)** 가 된다. (앱이 꺼져도 데이터는 디스크에 남는다.)
메모리에만 두고 싶다면 `jdbc:h2:mem:studyjpa` 처럼 `mem:` 을 쓴다.

**`application.properties` 예시**
```properties
# H2 웹 콘솔 켜기
spring.h2.console.enabled=true

# 파일 기반 DB (서버 모드) — ~/studyjpa 파일에 저장, 앱 종료 후에도 데이터 유지
spring.datasource.url=jdbc:h2:tcp://localhost/~/studyjpa
spring.datasource.username=sa
spring.datasource.password=

# 엔티티 보고 테이블 자동 생성 (학습용)
spring.jpa.hibernate.ddl-auto=create

# JPA가 날리는 SQL을 콘솔에 출력
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
```

**`application.yaml` 예시**
```properties
spring:
  application:
    name: studyjpa
  datasource:
    url:  jdbc:h2:tcp://localhost/~/studyjpa
    username: sa
    password:   
  jpa:
    hibernate:
      ddl-auto: create
    properties:
      hibernate:
        format_sql: true
    show-sql: true  
  h2:
    console:
      enabled: true
      path: /h2-console
```
---

### ddl-auto 옵션별 동작

| 값 | 시작할 때 | 끝날 때 | 데이터 |
|---|---|---|---|
| `create` | drop 후 create | 그대로 둠 | 시작 시마다 초기화 |
| `create-drop` | drop 후 create | **drop** | 시작 초기화 + 종료 시 삭제 |
| `update` | 없으면 만들고, 바뀐 것만 반영 | 그대로 둠 | **유지됨** |
| `validate` | 엔티티 ↔ 테이블 일치만 검사 (생성 X) | — | 유지됨 |
| `none` | 아무것도 안 함 | — | 유지됨 |

> `create` 와 `create-drop` 의 차이는 **데이터가 디스크에 남는 환경(파일 모드·기존 RDB)에서 드러난다.**
> 지금처럼 `~/studyjpa` 파일 기반 DB를 쓰면, 앱을 꺼도 파일은 남기 때문에
> `create`(종료 시 테이블 그대로 둠) 와 `create-drop`(종료 시 테이블 drop) 의 차이가 실제로 나타난다.
> 반대로 인메모리(`mem:`) DB라면 앱이 꺼질 때 DB 자체가 사라져 둘의 차이가 거의 드러나지 않는다.

---

#### 개발 / 학습 단계
- **`create` 또는 `create-drop`** — 엔티티를 자주 바꾸므로 매번 깨끗하게 새로 만드는 게 편하다.
  매핑 변경이 즉시 반영된다. (인메모리 H2 + 학습용으로 가장 흔함)
- **`update`** — 개발 중에도 데이터를 살려두고 싶을 때. 단, 컬럼 추가는 해주지만
  **컬럼 삭제·타입 변경은 제대로 반영하지 못하는** 한계가 있습니다.
  "분명 엔티티를 고쳤는데 반영이 안 되는" 현상의 원인이 되곤 합니다.

#### 테스트(통합 테스트) 단계
- **`create-drop`** — 테스트가 끝나면 테이블까지 정리되어 깔끔합니다.
  테스트마다 동일한 초기 상태를 보장하기 좋습니다.

#### 운영(Production) 단계
- **`validate`** — 엔티티와 실제 테이블 구조가 일치하는지 검증만 하고,
  스키마는 절대 건드리지 않습니다.
- **`none`** — 검증조차 하지 않음. 운영상태에서 주로 사용함.

> ⚠️ 운영에서는 `create` / `create-drop` 절대 금지.
> 배포할 때마다 실데이터가 통째로 삭제됩니다.

## 실전 예시를 통한 개념 설명

JPA 관련 개념에 대해선 개념 보다는 실제 예시를 통해서 단계별 설명 및 진행 합니다.

### 한눈에 보기

```
                 ┌────────────┐
                 │ DEPARTMENT │
                 └─────┬──────┘
                       │ 1:N (dept_id, NOT NULL)
                 ┌─────▼──────┐
       ┌─────────┤   MEMBER   ├──────────┐
       │ author  └─────┬──────┘  member  │
       │ 1:N           │ author   1:N    │
       │ NOT NULL      │ 1:N             │
 ┌─────▼─────┐   ┌─────▼──────┐   ┌──────▼─────┐
 │  COMMENT  │   │    POST    │   │  POST_LIKE │
 │  post_id  │───┤            ├───┤ (member_id,│
 │  NOT NULL │1:N│            │1:N│  post_id)  │  ← 복합키
 └───────────┘   └────────────┘   └────────────┘
   = Member × Post 연결(좋아요)을 복합키로 푼 테이블
```

---

### 관계 정리

| 관계 | 종류 | FK 컬럼 | 필수 |
|---|---|---|---|
| Member → Department | N:1 | `dept_id` | NOT NULL |
| Post → Member (작성자) | N:1 | `author_id` |  NOT NULL |
| Comment → Post | N:1 | `post_id` | NOT NULL |
| Comment → Member (작성자) | N:1 | `author_id` | NOT NULL |
| PostLike → Member | N:1 | `member_id` (PK 일부) |(PK) |
| PostLike → Post | N:1 | `post_id` (PK 일부) | (PK) |

### 한 줄 요약

> 회원·부서·게시글·댓글·좋아요의 5개 테이블. 모든 관계는 **N:1 단방향 + NOT NULL**,
> 감사(Audit) 칼럼은 상속(`BaseEntity`/`BaseTimeEntity`)으로, 좋아요는 **복합키 연결 테이블**로 구성.

## 엔티티 매핑 기초 — 어노테이션 살펴보기

JPA는 어노테이션 몇 개로 이 매핑을 표현합니다. 실제로 작성해 둔 `Member` 엔티티를 예시로 보자.

```java
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Member {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String email;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "dept_id", nullable = false)
    private Department dept;
}
```

| 어노테이션 | 역할 |
|---|---|
| `@Entity` | 이 클래스를 JPA가 관리하도록 선언. **없으면 매핑 자체가 안 됨** (필수) |
| `@Id` | 이 필드가 기본키(PK)임을 표시. **모든 엔티티에 필수** |
| `@GeneratedValue` | PK 값을 누가/어떻게 만들지 지정 
| `@Getter` | 모든 필드의 getter 메서드 자동 생성 |
| `@NoArgsConstructor(access = PROTECTED)`  | 인자 없는 protected 생성자 자동 생성 |
| `@ManyToOne` / `@JoinColumn` | 연관관계 매핑. **다음 챕터의 주제** |

> **`@ManyToOne(optional = false)` 의 `optional = false` 는?**
>
> "이 연관관계는 **필수**다 (= `dept`가 null이면 안 된다)" 라는 선언입니다.
> ERD에서 `dept_id`가 **NOT NULL**이었던 것과 같은 의미 — 모든 회원은 반드시 부서를 가집니다.
> JPA가 "`dept`가 비어 있을 수도 있다"는 가정 X **더 효율적인 쿼리(INNER JOIN 등)**를 만들 수 있다.
>
> 참고로 옆에 붙은 `@JoinColumn(nullable = false)` 는 같은 제약을 **DB 컬럼 차원**에서 거는 것
> 둘 다 NOT NULL을 의미하지만,
> 한쪽은 **객체 입장(optional)**, 한쪽은 **DB 입장(nullable)** 에서 표현한다.
>
> 실무에선 **둘 다 같이** 거는 것이 이상적이다.

> 테이블·컬럼 이름이나 길이, NOT NULL 같은 옵션을 더 세밀히 지정하고 싶다면
>
> `@Table(name="...")` / `@Column(name="...", length=..., nullable=...)` 을 붙인다.
> **기본값으로 충분하면 생략 가능**
> (ex: 클래스명 `Member` → 테이블명 `MEMBER`, 필드명 `name` → 컬럼명 `name`)

### @NoArgsConstructor 쓰지 않으면 어떻게 써야 하나?

위 코드에 붙은 `@NoArgsConstructor(access = AccessLevel.PROTECTED)` 한 줄이
없다면, 직접 이렇게 작성해야 합니다.

```java
@Entity
public class Member {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String email;
    // ... 필드들 ...

    protected Member() {}   // ← 인자 없는 protected 생성자가 반드시 필요
}
```

**왜 인자 없는 생성자가 필요한가**
JPA는 엔티티 객체를 만들 때 **리플렉션**으로 빈 객체부터 만든 뒤, 필드 값을 하나씩 채워 넣습니다.
지연 로딩(Lazy)을 위한 **프록시 객체**도 원본 클래스를 상속해서 만들면서 인자 없는 생성자를 호출하죠. 결국 인자 없는 생성자가 없으면 JPA가 객체를 만들 수단이 없다.

**왜 `public`이 아니라 `protected`인가?**
`public`으로 열어 두면 애플리케이션 코드 어디서든 `new Member()` 로
**필수 필드가 비어 있는 객체**를 만들 수 있게 됩니다. 객체 생성은
**정적 팩토리 메서드 / 의도된 생성자 / 빌더** 한 곳에서만 일어나도록
강제하는 게 안전합니다. `protected`로 두면 JPA(같은 패키지의 프록시)는 호출
가능하지만, **바깥 코드에서는 빈 엔티티를 만들 수 없습니다.**
(`private`은 프록시 상속이 안 되므로 불가)

### → 그래서 `@NoArgsConstructor(access = PROTECTED)`가 관례

`protected Member() {}` 를 모든 엔티티 클래스마다 적기보다
**어노테이션 한 줄로 대체하는 것이 JPA 엔티티의 관례**처럼 굳어졌다.

```java
@NoArgsConstructor(access = AccessLevel.PROTECTED)
```

위 `Member` 엔티티 상단에 이 어노테이션이 붙어 있는 이유입니다.

### @GeneratedValue — PK 자동 생성

`@Id` 만 있다면 PK 값을 우리가 직접 채워줘야 합니다. 그건 번거로우니
보통 `@GeneratedValue`로 **PK 생성을 DB에 맡깁니다.**

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

`IDENTITY`는 MySQL의 `AUTO_INCREMENT`, H2의 IDENTITY 컬럼처럼
**DB가 PK 값을 1씩 증가시켜 자동으로 만들어 주는** 방식입니다.


> 다른 전략(`SEQUENCE`, `TABLE`, `AUTO`)도 있지만 다른 DB(Oracle/PostgreSQL)를
> 쓰거나 성능 튜닝이 필요할 때 등장한다.

---

### @Column — 컬럼 옵션

위 `Member`에는 `@Column`이 안 보였지만, 다른 엔티티에는 등장합니다.
지금 코드에 쓰인 두 가지만 짚고 갑니다. (다른 옵션은 필요할 때 찾아보면 됩니다)

> [!NOTE]
> **자바 필드명 → DB 컬럼명은 자동 변환된다.**
> Spring Boot의 기본 네이밍 전략은 **camelCase → snake_case**.
> 예: `Department.deptCode` → `dept_code` 컬럼, `createdAt` → `created_at`.
> 그래서 `@Column(name = ...)` 을 따로 명시하지 않아도 컬럼명이 자연스럽게 결정됩니다.
> (테이블명도 마찬가지 — `PostLike` → `post_like`)

#### `length` — 문자열 길이 지정

```java
// Comment.java
@Column(length = 500)
private String content;
```

`String` 필드는 기본적으로 **`VARCHAR(255)`** 로 매핑됩니다.
댓글처럼 좀 더 긴 텍스트를 받아야 한다면 `length`로 늘립니다.
(DDL에만 영향 — JPA가 만들어주는 `create table ... varchar(500)` 부분이 바뀝니다.)

#### `updatable = false` — INSERT 한 번 후 더 이상 수정되지 않음

```java
// BaseTimeEntity.java
@CreatedDate
@Column(updatable = false)
private LocalDateTime createdAt;
```

JPA가 UPDATE SQL을 만들 때 **이 컬럼을 빼고** 만든다.
`createdAt`(생성 시각) · `createdBy`(작성자)

**최초 INSERT 한 번 박히면 그 뒤로 절대 바뀌면 안 되는 값**에 사용한다.

### @Lob — 대용량 텍스트/바이너리 매핑

`Post`의 `content`(게시글 본문)는 길어질 수 있습니다. 이런 필드에는 `@Lob`을 붙입니다.

```java
// Post.java
@Lob
private String content;
```

| 방식 | 결과 | 언제 / 왜 |
|---|---|---|
| `@Column(length = N)` | `VARCHAR(N)` | 수천 자 이내, 가장 단순 |
| `@Lob` | `CLOB`(문자) / `BLOB`(바이너리) | 길이 제한 없는 대용량, **DB 독립적** |
| `@Column(columnDefinition = "TEXT")` | DB의 `TEXT` 타입 직접 지정 | DB 타입을 콕 집어야 할 때, **DB 종속 주의** |

→ 지금 코드는 **DB 독립적이라 권장되는 `@Lob`** 을 선택했습니다.

### @ManyToOne — 연관관계의 시작

ERD에 있던 모든 N:1 관계 (`Member → Department`, `Post → Member`,
`Comment → Post`, `Comment → Member` …) 는 자바 객체에서 **그냥 참조**로 표현된다.

```java
// Member.java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "dept_id", nullable = false)
private Department dept;
```

JDBC라면 `private Long deptId;` 로 들고 다녔겠지만,
JPA에서는 **`Department` 객체 자체**를 들고 다닌다.

#### 어노테이션 의미

| 어노테이션 / 옵션 | 역할 |
|---|---|
| `@ManyToOne` | "이 필드(`dept`)는 N:1 관계의 N쪽" (회원 N : 부서 1) |
| `@JoinColumn(name = "dept_id")` | DB 테이블에서 FK 컬럼 이름 |
| `optional = false` | 이 연관관계는 **필수** (`dept`가 null이면 안 됨) — 객체 입장 |
| `nullable = false` | FK 컬럼 자체에 NOT NULL — DB 컬럼 입장 |
| `fetch = FetchType.LAZY` | **지연 로딩** (아래 자세히) |

#### `FetchType` — 즉시 로딩 vs 지연 로딩

`Member`를 조회했을 때 연결된 `Department`까지 **함께 즉시** 가져올지,
아니면 실제 `member.getDept()` 를 호출하는 **그 순간**에 가져올지의 차이입니다.

| 옵션 | 동작 | 쿼리 |
|---|---|---|
| `FetchType.EAGER` | **즉시** 같이 가져옴 | `Member` 조회 SQL에 `JOIN`이 자동으로 끼어듦 |
| `FetchType.LAZY` | 실제로 쓰는 **순간**에 별도 SQL | `member.getDept().getName()` 호출 시 SQL 실행 |

> [!CAUTION]
> **`@ManyToOne`의 기본값은 `EAGER`** 입니다. 하지만 실무에서는
> **`LAZY`를 거의 항상 명시**하는 게 관례입니다.
>
> 이유: `EAGER`로 두면 의도치 않은 JOIN이 여기저기서 발생해
> **N+1 문제** 등 성능 사고가 잘 납니다. `LAZY`로 두면
> "내가 필요할 때만 가져온다"가 명확해집니다. (N+1은 별도 챕터에서)

#### `Department` 객체가 안 들어 있어도 작동하는 비밀 — 프록시

`fetch = LAZY` 일 때 `em.find(Member.class, 1L)` 를 호출하면,
`member.dept` 자리에는 **진짜 `Department` 객체가 아니라 "프록시" 객체** 가 들어갑니다.
프록시는 `Department`를 **상속한 가짜 객체**. `member.getDept().getName()` 처럼
**실제 값을 꺼내려는 순간**에 SQL이 나가서 진짜 값을 채워 옵니다.

→ 앞에서 본 "기본 생성자가 `protected` 이상으로 열려 있어야 한다" 의 이유가 바로 여기 있다.
프록시 객체가 `Department`를 상속하면서 인자 없는 생성자를 호출해야 하기 때문이다.

## 상속 매핑 — `@MappedSuperclass` + Auditing

다섯 테이블 전부 `createdAt` / `updatedAt` / `createdBy` / `updatedBy`를 가진다면,
같은 필드를 다섯 번 적게 됩니다. 공통 필드는 **부모 클래스로 빼는 것이 정석**.

```
BaseTimeEntity   (createdAt, updatedAt)
      ▲
      │ extends
BaseEntity       (+ createdBy, updatedBy)
      ▲
      │ extends
  Post / Comment
```

### `@MappedSuperclass` — 매핑 정보만 상속, 테이블은 안 만듦

```java
// BaseTimeEntity.java
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public class BaseTimeEntity {

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}
```

| 어노테이션 | 역할 |
|---|---|
| `@MappedSuperclass` | "**매핑 정보만 자식에게 물려준다. 본인은 테이블로 만들지 않는다.**" |
| `@EntityListeners(AuditingEntityListener.class)` | 엔티티의 저장·수정 이벤트를 감지해 시간/사용자 정보를 자동으로 채워주는 리스너 등록 |
| `@CreatedDate` | INSERT 시점에 현재 시각 자동 세팅 |
| `@LastModifiedDate` | INSERT/UPDATE 시점에 현재 시각 자동 세팅 |
| `@CreatedBy` / `@LastModifiedBy` | 작성자/수정자 ID 자동 세팅 |

> `@MappedSuperclass` 가 없으면 JPA가 `BaseTimeEntity` 자체를 테이블로 만들려고 합니다.
> **"필드만 자식에게 물려주고 테이블은 만들지 마"** 의 의미.

### 왜 두 단계로 나눴나? — `BaseTimeEntity` ⊂ `BaseEntity`

- `BaseTimeEntity`: 시간만 (createdAt, updatedAt)
- `BaseEntity`: 시간 + 사용자 (createdBy, updatedBy)

| 엔티티 | 상속 | 가지는 감사 정보 |
|---|---|---|
| `Post`, `Comment` | `BaseEntity` | 시간 + 사용자 |
| `PostLike` | `BaseTimeEntity` | 시간 |
| `Member`, `Department` | (없음) | 없음 |

→ "좋아요 누른 시간"은 기록하고 싶지만 "누른 사람"은 이미 PK(`member_id`)로 알 수 있으니
`createdBy`를 안 받는 식으로 **상속 단계별로 차등**을 두는게 이상적이다.

### Auditing을 실제로 작동시키려면 — `@EnableJpaAuditing`

`@EntityListeners` 만 붙인다고 자동으로 동작하지 않습니다.
Spring Boot 메인 클래스(또는 설정 클래스)에 한 줄 더 필요합니다.

```java
@SpringBootApplication
@EnableJpaAuditing
public class StudyJpaApplication { ... }
```

> `createdBy` / `updatedBy` 까지 자동 채우려면 추가로
> `AuditorAware<Long>` Bean을 등록해야 합니다 (현재 로그인 사용자의 ID를 제공).
> 일단 여기까지는 "이런 게 필요하다" 정도로만 기억한다.

## 복합키 매핑 — `@EmbeddedId` + `@MapsId`

`PostLike`는 "어떤 회원이 어떤 글에 좋아요를 눌렀나"를 저장하는 **연결 테이블**입니다.
같은 회원이 같은 글에 두 번 좋아요 누를 수 없으니, **(member_id, post_id) 자체가 PK**.
이게 바로 **복합키(Composite Key)** 입니다.

### 1단계 — PK 전용 클래스 만들기 (`@Embeddable`)

```java
// PostLikeId.java
@Embeddable
@Getter
@EqualsAndHashCode
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class PostLikeId implements Serializable {

    private Long memberId;
    private Long postId;

    public PostLikeId(Long memberId, Long postId) {
        this.memberId = memberId;
        this.postId = postId;
    }
}
```

| 요구사항 | 이유 |
|---|---|
| `@Embeddable` | "엔티티에 끼워 넣을 수 있는 값 객체"임을 선언 |
| `Serializable` 구현 | JPA 표준 요구사항|
| `equals` / `hashCode` 구현 | **1차 캐시가 객체 동일성 비교에 사용함** — 안 만들면 같은 PK인데 다른 객체로 인식됨 |
| `protected` 기본 생성자 | 일반 엔티티와 같은 이유|

> Lombok의 `@EqualsAndHashCode`가 복합키 클래스에 거의 필수로 따라붙는 이유입니다.

### 2단계 — 엔티티에 끼워 넣기 (`@EmbeddedId` + `@MapsId`)

```java
// PostLike.java
@Entity
public class PostLike extends BaseTimeEntity {

    @EmbeddedId
    private PostLikeId id;

    @MapsId("memberId")          // ← 핵심
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "member_id")
    private Member member;

    @MapsId("postId")            // ← 핵심
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "post_id")
    private Post post;

    public PostLike(Member member, Post post) {
        this.member = member;
        this.post = post;
    }
}
```

| 어노테이션 | 역할 |
|---|---|
| `@EmbeddedId` | "이 필드(`id`)가 복합 PK다. 타입은 `@Embeddable` 클래스" |
| `@MapsId("memberId")` | **`member` 연관관계의 PK를 `id.memberId`로 매핑하라** — FK가 PK의 일부 |
| `@JoinColumn(name = "member_id")` | 실제 DB FK 컬럼 이름 |

### `@MapsId`가 하는 일 — 신기한 생성자의 비밀

`PostLike` 생성자를 다시 보면 한 가지 어색한 점이 있다 — `id`를 직접 세팅하지 않는데도 동작합니다.

```java
public PostLike(Member member, Post post) {
    this.member = member;
    this.post = post;
    // this.id = ???   ← 안 적어도 된다!
}
```

비밀은 `@MapsId`입니다. JPA에게
**"엔티티 저장 시 `member.getId()` 를 `id.memberId` 에 자동 복사해라"** 라고
알려주는 역할이라서, 개발자가 PK를 직접 다루지 않아도 알아서 채워집니다.

### 결과로 만들어지는 테이블

```sql
CREATE TABLE post_like (
    member_id  BIGINT NOT NULL,
    post_id    BIGINT NOT NULL,
    created_at TIMESTAMP,                       -- BaseTimeEntity 상속
    PRIMARY KEY (member_id, post_id),           -- 복합 PK
    FOREIGN KEY (member_id) REFERENCES member(id),
    FOREIGN KEY (post_id)   REFERENCES post(id)
);
```

> [!NOTE]
> 복합키는 처음 보면 헷갈릴 수 있다.
> 대안으로 `id BIGINT AUTO_INCREMENT` 를 두고 `UNIQUE(member_id, post_id)` 만 거는
> 방식도 흔합니다. **JPA로는 후자가 훨씬 간단**합니다.
> 어느 쪽이 더 나은지는 팀 선호와 도메인에 따라 다르며, 이번 코드는 **JPA의 복합키
> 매핑 방식을 익히는 학습 목적**으로 전자를 선택한 것으로 보면 된다.

> 아래의 코드가 지금 위의 Note에 대해서 설명한 내용이다.

```java
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@Table(
        uniqueConstraints = @UniqueConstraint(
                name = "uk_member_post",
                columnNames = {"member_id", "post_id"}
        )
)
public class PostLikeSurrogate extends BaseTimeEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "member_id", nullable = false)
    private Member member;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "post_id", nullable = false)
    private Post post;

    public PostLikeSurrogate(Member member, Post post) {
        this.member = member;
        this.post = post;
    }
}

```

## "엔티티에 메서드(비즈니스 로직) 넣어도 되나?"

주니어가 자주 듣는 말 — *"엔티티에 비즈니스 메서드 넣지 마라"*.
**결론부터: 그건 절대 규칙이 아니고, 오히려 의견이 갈리는 주제이다.**


**A — 빈약한 도메인 모델 (Anemic Domain Model)**
- 엔티티는 데이터만 담는 그릇 (필드 + getter/setter)
- 모든 비즈니스 로직은 Service에 둔다.

```java
// 엔티티는 데이터만, 로직은 서비스가 끌고 다님
member.setPoint(member.getPoint() - amount);  // 엔티티는 수동적
```

**B — 풍부한 도메인 모델 (Rich Domain Model, DDD)**
- 엔티티가 자기 데이터에 대한 규칙을 스스로 가진다
- Martin Fowler는 오히려 A를 **안티패턴**이라 부름

```java
@Entity
public class Member {
    private int point;

    // 자기 상태에 대한 규칙을 스스로 책임짐
    public void usePoint(int amount) {
        if (this.point < amount) throw new IllegalStateException("포인트 부족");
        this.point -= amount;
    }
}
```

> "엔티티에 비즈니스 메서드 넣지 마라"는
> 보편 진리가 아니기 때문에, 판단에 의해서 사용하길 권장한다.

### "진짜 관례"는 두 가지

**① Setter는 만들지 않는다**

```java
// 무분별한 setter — 누가 언제 왜 바꿨는지 알 수 없음
member.setPoint(9999);
member.setName("");

// 의도가 드러나는 메서드로
member.usePoint(500);
member.changeName("홍길동");
```

"메서드를 넣지 마라"가 아니라 **"setter 대신 의도가 드러나는 메서드를 넣어라"**가 정확한 표현.

**② 외부 의존이 필요한 로직은 엔티티에 넣지 않는다**
```java
@Entity
public class Member {

    // 자기 데이터만으로 작성 가능한 로직
    public void usePoint(int amount) {
        if (this.point < amount) throw new IllegalStateException();
        this.point -= amount;
    }

    // 외부 의존 로직
    public void join() {
        memberRepository.save(this);   // 엔티티가 Repository를 알면 안 됨
        emailService.sendWelcome();    // 외부 시스템 의존 → Service의 일
    }
}
```
