## 0단계. 복습 — 4주차의 그 함정 (LazyInitializationException)

- 프록시는 **통로(트랜잭션)** 가 살아있어야 값을 채운다 → 닫히면 터진다. (4주차 6단계 회수)
- 이번 주는 그 통로 문제를 푸는 **4가지 방법** 을 본다: Fetch Join / `@EntityGraph` / DTO / OSIV.
- 그런데 그 전에, N+1을 보여줄 **무대(연관관계)** 부터 깔아야 한다. → 1단계.

> [!Note]
> **준영속 상태에서 생기는 또 다른 함정 — merge 함정 (4주차에서 예고한 내용)**
>
> 트랜잭션이 끝난 뒤 반환된 엔티티(준영속)에 `save()`를 호출하면, 내부에서 `merge()`가 실행된다.
> `merge()`는 원본을 영속화하는 게 아니라 **복사본을 새로 만들어 반환**하므로,
> 반환값을 버리고 원본을 수정하면 변경 감지가 동작하지 않는다.
>
> ```java
> Member detached = memberService.findMember(1L); // 트랜잭션 밖 → 준영속
>
> memberRepository.save(detached);   // ❌ 반환값 버림 — 원본은 여전히 준영속
> detached.changeName("새이름");      // 변경 감지 안 됨 → DB 반영 X
>
> Member managed = memberRepository.save(detached); // ✅ 반환값을 받아야
> managed.changeName("새이름");       // managed가 영속 상태 → DB 반영 O
> ```
>
> **핵심:** `save()`의 반환값을 항상 받아서 사용할 것. 준영속 엔티티에 `save()`를 쓸 때 원본을 계속 쓰는 건 함정이다.

## 1단계. 연관관계 매핑 — 양방향과 연관관계의 주인

> 예시 엔티티: `Department 1 : N Member` (또는 게시판 `Post 1 : N Comment`)

4주차까지 우리는 `Member` 가 `Department` 를 참조하는 **단방향(`N:1`)** 만 썼다. 회원에서 부서는 찾아갈 수 있지만(`member.getDept()`), 그 반대 — **부서에서 소속 회원 목록** — 은 아직 객체로 탐색할 수 없다. 이번 단계에서 그 반대 방향을 열어주는 **양방향 매핑**을 본다. 그리고 이 양방향이 곧 2단계 **N+1 문제의 무대**가 된다.

### 단방향 vs 양방향 — 왜 양방향인가

먼저 분명히 할 것 — **양방향이 "더 발전된 것" 이 아니다.** 반대 방향 탐색이 **실제로 필요할 때만** 추가하는 것이고, 필요 없으면 단방향이 더 낫다(객체가 단순해진다).

```java
// before — 단방향. Member 만 Department 를 안다.
@Entity
public class Member {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")   // FK 는 member 테이블에 있다
    private Department dept;
}

// after — 양방향. Department 도 자기 회원들을 알게 된다.
@Entity
public class Department {

    @OneToMany(mappedBy = "dept")          // ← "나는 주인이 아니다" 선언 (아래 설명)
    private List<Member> members = new ArrayList<>();
}
```

> **중요 — 양방향이 돼도 테이블은 그대로다.** 새 컬럼이나 FK 가 생기지 않는다. FK 는 여전히 `member.department_id` **하나**뿐이고, 양방향은 순전히 **객체 탐색의 편의** 를 위해 자바 쪽에 참조를 하나 더 둔 것이다. 이 "객체엔 참조가 둘, 테이블엔 FK 하나" 라는 불일치가 다음 이야기의 출발점이다.

### 연관관계의 주인 — mappedBy 는 "거울" 표시다

객체에는 참조가 둘이다 — `member.dept` 와 `dept.members`. 그런데 테이블의 FK 는 `member.department_id` **하나**다. 그럼 JPA 는 회원의 부서가 바뀌었을 때 **어느 쪽 참조를 보고 FK 를 UPDATE** 해야 할까?

JPA 의 답은 명확하다 — **둘 중 하나를 "주인" 으로 정하고, 주인만 FK 를 쓴다(INSERT/UPDATE).** 나머지 한쪽은 **읽기 전용 거울**이다.

- **주인 = FK 를 가진 쪽** = `N` 쪽 = `Member.dept`
- `mappedBy = "dept"` 는 주인이 **아닌** 쪽(`Department.members`)에 붙여 **"나는 `Member` 의 `dept` 필드에 의해 매핑되는 거울일 뿐, FK 를 직접 제어하지 않는다"** 를 선언한다.

**어느 쪽이 주인인지는 애너테이션으로 바로 보인다.**

| 애너테이션 | 역할 | FK |
| --- | --- | --- |
| `@ManyToOne` | **주인** | 가짐 |
| `@OneToMany(mappedBy = "…")` | **거울** | 없음 |

이렇게 갈리는 이유는 **`1:N` 의 FK 가 언제나 `N`(다) 쪽 테이블에** 있기 때문이다. `member` 한 행은 `dept_id` **하나**를 갖지만, `department` 는 여러 회원의 FK 를 한 컬럼에 담을 수 없다. 그래서 FK 를 자연히 가진 `@ManyToOne` 쪽이 주인이 되고, `@OneToMany(mappedBy=…)` 가 거울이 된다.

> [!Caution]
> **주인은 "더 중요한/부모 엔티티" 가 아니라 "FK 를 가진 쪽" 이다.** 게시판 `Post 1:N Comment` 에서 글이 더 중심처럼 보여도, FK(`post_id`)는 `comment` 에 있으므로 **주인은 `Comment`**, `Post` 는 거울이다. 주인은 오직 **FK 위치**로만 판단한다.

> [!Note]
> **주인/거울은 "클래스" 가 아니라 "관계마다" 정해진다.** 한 엔티티가 관계에 따라 주인도, 거울도 될 수 있다 — `Post` 가 그 예다.
> - `Post ↔ Comment` 에선 **거울** (`@OneToMany(mappedBy = "post")`)
> - `Post ↔ Member`(작성자) 에선 **주인** (`@ManyToOne`, `author_id` FK 보유)

> **왜 주인을 정하는가:** 양쪽이 동시에 FK 를 제어하면, 한쪽에선 "A부서", 다른 쪽에선 "B부서" 로 바꿨을 때 **어느 값으로 UPDATE 할지 충돌**한다. 쓰기 책임을 **한 곳(주인)** 으로 모아 이 모호함을 없애는 것이다.

> [!Caution]
> **거울(`mappedBy`) 쪽에만 값을 넣으면 DB 에 반영되지 않는다.** 가장 흔한 양방향 버그다.
>
> ```java
> department.getMembers().add(member);   // ❌ 거울에만 추가 → FK 안 바뀜 (JPA 가 무시)
> member.changeDept(department);          // ✅ 주인(member.dept)을 바꿔야 FK 가 UPDATE 된다
> ```

### 연관관계 편의 메서드 — 양쪽을 한 번에 맞춘다

그렇다고 주인만 세팅하면 끝일까? 아니다. **DB 는 맞지만 메모리가 어긋난다.** 같은 트랜잭션 안에서 `department.getMembers()` 를 보면, 방금 바꾼 회원이 **거기엔 없는** 상태가 된다(거울을 안 건드렸으니까). 1차 캐시에 들고 있던 그 `Department` 객체를 누가 다시 보면 옛 목록을 보게 된다.

그래서 양방향에서는 **양쪽 참조를 항상 같이 맞춰주는** 편의 메서드를 둔다.

```java
@Entity
public class Member {

    // 주인 쪽(Member)에 편의 메서드를 둔다
    public void changeDept(Department dept) {
        this.dept = dept;               // ① 주인 쪽 — FK 가 여기서 결정된다
        dept.getMembers().add(this);    // ② 거울 쪽 — 메모리 일관성을 맞춘다
    }
}
```

```java
// 호출부 — 한 줄로 양쪽이 동기화된다
member.changeDept(salesDept);
// 이제 member.getDept() 도, salesDept.getMembers() 도 서로를 올바로 가리킨다
```

> **핵심:** 양방향은 "참조가 둘" 이므로 **둘을 함께 세팅하지 않으면 메모리와 DB 가 어긋난다.** 편의 메서드는 그 두 줄을 **한 곳에 묶어** 빠뜨릴 수 없게 만드는 장치다.

> [!Note]
> **편의 메서드를 어디 두나 — 주인 여부와 무관하다.** "그 동작이 자연스러운 쪽 + 컬렉션을 가진 쪽" 에 둔다.
> - `회원이 부서를 바꾼다` → 회원의 단일 동작 → **`Member`**(주인) 에 `changeDept`
> - `글에 댓글을 추가/삭제한다` → 글이 거느린 컬렉션 관리 → **`Post`**(거울이어도!) 에 `addComment`/`removeComment`
>
> 위치가 주인이든 거울이든, **메서드 안에서 양쪽(주인 FK + 거울 컬렉션)을 다 세팅**한다는 점은 똑같다. (그래서 주인을 정하는 것과 편의 메서드를 어디 두는지는 **별개의 결정**이다)

### 흔한 함정 — 무한 순환

양방향이 되면 `Member` → `Department` → `members` → `Member` → … 로 **서로를 끝없이 참조**할 수 있다. 그래서 `toString()` 을 양쪽 연관까지 찍게 만들거나, 엔티티를 그대로 JSON 으로 직렬화하면 **무한 루프(StackOverflow)** 가 난다.

- `toString()` 에는 **연관 필드를 빼고** 자기 필드만 넣는다. (`@ToString(exclude = ...)`)
- API 응답은 엔티티를 직접 내보내지 말고 **전용 응답 객체(DTO)로 변환** 해서 내보낸다.

> 이제 "부서에서 회원 목록을 꺼낸다" 는 이 양방향 탐색이 준비됐다. 이게 LAZY 와 만나면 어떻게 쿼리를 폭발시키는지 — 바로 다음 2단계 **N+1** 이다.

## 2단계. N+1 문제 — LAZY의 그림자

### 왜 N+1이 생기나

- 목록 조회 1번(1) + 각 row 의 연관 엔티티 접근마다 추가 쿼리(N) = **1 + N**.
- `show-sql` 로 **N번 찍히는 걸 직접 눈으로** 확인. (4주차의 hands-on 톤 유지)

### ⚠️ EAGER는 답이 아니다

- 학생 본능: "그럼 `fetch = EAGER` 로 바꾸면 되잖아?"
- ⚠️ EAGER 는 **더 나쁘다** — 항상·모든 곳에서 조인이 끌려와 통제 불가, 페이징·성능 문제.
- 결론: **기본은 LAZY 로 두고, 필요할 때만 당겨오는** 게 정석 → 3단계.

## 3단계. Fetch Join — 한 방에 같이 가져오기

### JOIN FETCH 문법

- `SELECT m FROM Member m JOIN FETCH m.dept` — 연관 엔티티를 **조인해서 한 번에**.
- N+1 → **쿼리 1번** 으로 줄어드는 원리.

### ⚠️ Fetch Join의 함정 세 가지

- **페이징** — 컬렉션(`1:N`) fetch join + 페이징은 위험(메모리 페이징으로 빠짐).
- **중복 row** — `1:N` 조인은 행이 뻥튀기됨 → `DISTINCT` 필요.
- **컬렉션은 하나만** — 둘 이상 컬렉션 fetch join 금지(카테시안 곱).

> 위 함정 세 가지는 전부 **`1:N` 컬렉션**에서만 생긴다. 이번 주는 `N:1`(`Member → Department`)까지만 다루므로 여기선 "이런 게 있다" 만 짚고, 자세한 해결(`DISTINCT`·batch fetch size)은 **보충자료**에서 본다.

> [!Note]
> **참고) @EntityGraph — 같은 효과를 애너테이션으로**
>
> Fetch Join 과 **같은 일(연관을 함께 로딩)** 을, JPQL 을 적지 않고 애너테이션만으로 낼 수 있다.
> 특히 `findAll`·`findById` 처럼 **우리가 쿼리를 못 적는 기본 제공 메서드**나 쿼리 메서드 위에 얹을 때 유용하다.
>
> ```java
> // JPQL 로 fetch join 을 쓰는 대신…
> @Query("SELECT m FROM Member m JOIN FETCH m.dept")
> List<Member> findAllWithDept();
>
> // 애너테이션만으로 같은 효과. 상속받은 findAll 을 그대로 두고 'dept 를 함께' 만 선언
> @EntityGraph(attributePaths = {"dept"})
> List<Member> findAll();
> ```
>
> **언제 무엇을:** 단순히 "같이 가져오기" 만이면 `@EntityGraph`, 조건·정렬·조인이 복잡하면 Fetch Join(JPQL).
> (단 `@EntityGraph` 는 항상 LEFT OUTER JOIN 이고, 컬렉션이면 Fetch Join 과 똑같은 페이징 함정을 가진다.)

## 4단계. DTO 프로젝션 — 애초에 엔티티를 안 만든다

- 필요한 컬럼만 `SELECT new ...Dto(m.name, m.dept.name)` → **프록시·N+1 자체가 안 생김**.
- 조회 전용 화면(목록/리포트)엔 DTO 가 정석.

### ⚠️ 트레이드오프 — DTO는 변경 감지가 안 된다

- DTO 는 영속 객체가 아니므로 **읽기 전용**. 값 바꿔도 UPDATE 안 나감(당연).
- 그래서 **"읽기만 할 화면 → DTO", "수정도 할 흐름 → 엔티티 + fetch join"** 으로 갈린다.

---

## 5단계. OSIV — 편함과 위험의 트레이드오프

### OSIV란?

- Open-Session-In-View = 요청이 끝날 때까지 **영속성 컨텍스트를 살려둠**.
- 그래서 컨트롤러/뷰에서 LAZY 를 건드려도 안 터진다. (4주차 함정이 "안 생기는" 이유)

### 켜기 vs 끄기

- 켜기(스프링 기본값): 편하다. 하지만 ⚠️ **DB 커넥션을 요청 내내 붙잡아** 성능·확장성 발목.
- 끄기: 커넥션을 빨리 반납. 대신 LAZY 를 **트랜잭션 안에서 미리 처리**(fetch join/DTO)해야 함.
- 실무 권장: **OSIV off + 명시적 조회(fetch join / DTO)**.

> [!Caution]
> OSIV를 끄면 서비스 트랜잭션이 끝나는 순간 반환된 엔티티가 **준영속**이 된다.
> 이 엔티티를 컨트롤러에서 다시 `save()`하면 0단계에서 본 **merge 함정**이 그대로 터진다.
> OSIV off를 선택했다면 **반환값을 DTO로 변환하거나, save() 반환값을 반드시 사용**해야 한다.

---

## 6단계. 선택 기준 — 언제 무엇을

| 상황 | 권장 | 이유 |
| --- | --- | --- |
| 단건 + 연관 몇 개, 수정도 함 | Fetch Join / `@EntityGraph` | 엔티티 유지 → 변경 감지 가능 |
| 목록·리포트 (읽기 전용) | DTO 프로젝션 | 프록시·N+1 원천 차단 |
| 전역 LAZY 편의 | (지양) OSIV on | 편하지만 커넥션 비용 |

---

## 한 줄 요약

> N+1 은 **LAZY 의 그림자** 다.
> 트랜잭션 안에서 미리 당겨오거나(**Fetch Join · `@EntityGraph`**),
> 애초에 엔티티를 안 만들거나(**DTO**),
> 통로를 늘리거나(**OSIV**) — **각각 대가가 다르다.**
> 정공법은 LAZY 를 기본으로 두고 **필요할 때만 명시적으로 당겨오는** 것.
