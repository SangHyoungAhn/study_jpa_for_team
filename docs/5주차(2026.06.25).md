## 0단계. 복습 — 4주차 내용 중 **LazyInitializationException**

> [!Note]
> **용어 정리 — JPA / Hibernate / Spring Data JPA** 
>
> | 층 | 정체 | 예 |
> | --- | --- | --- |
> | **JPA** | 표준(명세) — "이렇게 동작하라" 는 약속 | `@Entity`, `EntityManager`, JPQL |
> | **Hibernate** | JPA 를 실제로 구현한 **엔진** (가장 널리 씀) | 프록시·1차 캐시·SQL 생성·`PersistentBag` |
> | **Spring Data JPA** | 위를 더 쉽게 쓰게 해주는 스프링 모듈 | `JpaRepository`, `@Query` |
>
> 우리가 `@Entity`·`EntityManager` 같은 **JPA 표준**으로 코드를 적으면, 뒤에서 **실제로 프록시를 만들고 1차 캐시를 굴리고 SQL 을 짜는 일꾼이 Hibernate** 다. 그래서 본문이 "JPA 가" 가 아니라 "**Hibernate 가** 프록시를…" 라고 말한다.

4주차에서 우리는 프록시가 **통로(트랜잭션)** 가 살아 있어야만 값을 채울 수 있고, 그 통로가 닫힌 뒤에 프록시를 건드리면 `LazyInitializationException` 이 터진다는 것을 보았다. 그런데 통로 문제는 여기서 끝나지 않는다. 통로가 **열려 있어도** 또 다른 함정이 기다린다. 목록을 순회하며 각 row 의 프록시를 하나씩 깨우다 보면, 그때마다 별도의 쿼리가 한 번씩 더 나가 결국 쿼리가 N번 추가된다. 이것이 2단계에서 다룰 **N+1** 이다. 말하자면 통로 문제에는 N+1 이 사촌처럼 늘 붙어 다니는 셈이다.

이번 주는 이 두 문제를 **세 갈래**의 전략으로 푼다. 
- 첫째, **트랜잭션 안에서 연관을 미리 당겨오는** 방법으로, Fetch Join 과 `@EntityGraph` 가 여기에 속한다(이 둘은 JPQL 로 쓰느냐 애너테이션으로 쓰느냐의 차이일 뿐, 본질은 *같은 방법* 이다).
- 둘째, **애초에 엔티티(프록시)를 만들지 않는** 방법인 DTO 프로젝션이고, 
- 셋째, **통로 자체를 닫지 않는** 방법인 OSIV 다.

이번 주(본편)는 이 중 **첫째(Fetch Join·`@EntityGraph`)** 까지 다루고, **둘째(DTO)·셋째(OSIV)** 는 **다음 주차(조회 전략)** 에서 이어 본다. 그 전에, N+1 이 실제로 벌어질 **연관관계 매핑(양방향과 연관관계의 주인)** 부터 1단계에서 진행해야 한다.

## 1단계. 연관관계 매핑 — 양방향과 연관관계의 주인

> 예시 엔티티: `Department 1 : N Member` (또는 게시판 `Post 1 : N Comment`)

4주차까지 우리는 `Member` 가 `Department` 를 참조하는 **단방향(`N:1`)** 만 썼다. 회원에서 부서는 찾아갈 수 있지만(`member.getDept()`), 그 반대 — **부서에서 소속 회원 목록** — 은 아직 객체로 탐색할 수 없다. 이번 단계에서 그 반대 방향을 열어주는 **양방향 매핑**을 본다. 그리고 이 양방향이 곧 2단계 **N+1 문제의 무대**가 된다.

### 단방향 vs 양방향 — 왜 양방향인가

먼저 분명히 할 것 — **양방향이 "더 발전된 것" 이 아니다.** 반대 방향 탐색이 **실제로 필요할 때만** 추가하는 것이고, 필요 없으면 단방향이 더 낫다(객체가 단순해진다).

```java
// before — 단방향. Member 만 Department 를 안다.
@Entity
public class Member {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "dept_id")   // FK 는 member 테이블에 있다
    private Department dept;
}

// after — 양방향. Department 도 자기 회원들을 알게 된다.
@Entity
public class Department {

    @OneToMany(mappedBy = "dept")          // ← "여기서 dept는 Member에서 private Department dept" 선언
    private List<Member> members = new ArrayList<>();
}
```

> **중요 — 양방향이 돼도 테이블은 그대로다.** 새 컬럼이나 FK 가 생기지 않는다. FK 는 여전히 `member.dept_id` **하나**뿐이고, 양방향은 순전히 **객체 탐색의 편의** 를 위해 자바 쪽에 참조를 하나 더 둔 것이다. 이 "객체엔 참조가 둘, 테이블엔 FK 하나" 라는 불일치가 다음 이야기의 출발점이다.

위 코드에서 컬렉션을 `= new ArrayList<>()` 로 **초기화한 이유**는 한마디로 **`null` 이라는 상태를 없애 NullPointerException(NPE) 를 막기 위해서**다.
`new` 로 갓 만든(아직 영속화 전) 객체에는 Hibernate 가 개입하지 않으므로, 내가 초기화하지 않으면 `members` 는 `null` 이고, 편의 메서드의 `dept.getMembers().add(...)` 가 그 위에서 터진다.


| 구간 | 초기화 안 하면 (`List<Member> members;`) | 초기화 하면 (`= new ArrayList<>()`) |
| --- | --- | --- |
| `new` 직후 (영속화 전) | `null` → `getMembers().add()` 호출 시 **NPE** | 빈 리스트 → 안전하게 add·순회 |
| `findById` 등 DB 조회 후 | Hibernate 가 자기 컬렉션(`PersistentBag`)으로 **교체** | (동일 — 내 `ArrayList` 는 버려진다) |

> **핵심:** 컬렉션은 "비었거나 / 값이 있거나" **두 상태만** 갖게 하고 `null` 을 없앤다 → NPE 도, 널 체크도 사라진다. (생성자 말고 **필드 선언에서** 초기화해야 어떤 생성자로 만들든 항상 보장된다.)

### 연관관계의 주인 — mappedBy 는 "거울" 표시다

객체에는 참조가 둘이다 — `member.dept` 와 `dept.members`. 그런데 테이블의 FK 는 `member.dept_id` **하나**다. 그럼 JPA 는 회원의 부서가 바뀌었을 때 **어느 쪽 참조를 보고 FK 를 UPDATE** 해야 할까?

JPA 의 답은 명확하다 — **둘 중 하나를 "주인" 으로 정하고, 주인만 FK 를 쓴다(INSERT/UPDATE).** 나머지 한쪽은 **읽기 전용 거울**이다.

- **주인 = FK 를 가진 쪽** = `N` 쪽 = `Member.dept`
- `mappedBy = "dept"` 는 주인이 **아닌** 쪽(`Department.members`)에 붙여 **"나는 `Member` 의 `dept` 필드에 의해 매핑되는 거울일 뿐, FK 를 직접 제어하지 않는다"** 를 선언한다.

**어느 쪽이 주인인지는 애너테이션으로 바로 보인다.**

| 애너테이션 | 역할 | FK |
| --- | --- | --- |
| `@ManyToOne` | **주인** | 가짐 |
| `@OneToMany(mappedBy = "…")` | **거울** | 없음 |

이유는 **`1:N` 의 FK 가 대부분 `N`(다) 쪽 테이블에** 있기 때문이다. `member` 한 행은 `dept_id` **하나**를 갖지만, `department` 는 여러 회원의 FK 를 한 컬럼에 담을 수 없다. 그래서 FK 를 자연히 가진 `@ManyToOne` 쪽이 주인이 되고, `@OneToMany(mappedBy=…)` 가 거울이 된다.

> [!Caution]
> **주인은 "더 중요한/부모 엔티티" 가 아니라 "FK 를 가진 쪽" 이다.** 게시판 `Post 1:N Comment` 에서 글이 더 중심처럼 보여도, FK(`post_id`)는 `comment` 에 있으므로 **주인은 `Comment`**, `Post` 는 거울이다. 주인은 오직 **FK 위치**로만 판단한다.

> [!Note]
> **주인/거울은 "클래스" 가 아니라 "관계마다" 정해진다.** 한 엔티티가 관계에 따라 주인도, 거울도 될 수 있다 — `Post` 가 그 예다.
> - `Post ↔ Comment` 에선 **거울** (`@OneToMany(mappedBy = "post")`)
> - `Post ↔ Member`(작성자) 에선 **주인** (`@ManyToOne`, `author_id` FK 보유)

> **왜 주인을 정하는가:** 양쪽이 동시에 FK 를 제어하면, 한쪽에선 "A부서", 다른 쪽에선 "B부서" 로 바꿨을 때 **어느 값으로 UPDATE 할지 충돌**한다. 쓰기 책임을 **한 곳(주인)** 으로 모아 이 모호함을 없애는 것이다.

> [!Caution]
> **거울(`mappedBy`) 쪽에만 값을 넣으면 DB 에 반영되지 않는다.** 가장 흔한 양방향 버그다.
>
> ```java
> department.getMembers().add(member);   // ❌ 거울에만 추가 → FK 안 바뀜 (JPA 가 무시)
> member.changeDept(department);          // ✅ 주인(member.dept)을 바꿔야 FK 가 UPDATE 된다
> ```

근본을 한 줄로 정리하면 — **FK 컬럼은 하나뿐이니, 그것을 책임지는 자바 필드도 하나여야 한다.** 주인은 그 하나를 지정하는 것이고, `mappedBy` 는 나머지 한쪽을 "쓰기에서 빼라" 고 선언하는 것이다. JPA 는 `flush` 때 **주인 필드만 보고** FK SQL 을 만든다.

| 구분 | 무엇을 지정하나 | `flush` 때 JPA 의 행동 |
| --- | --- | --- |
| **주인** (`@ManyToOne`) | FK 컬럼 ↔ 자바 필드 매핑 | 이 필드를 보고 FK INSERT/UPDATE |
| **거울** (`@OneToMany(mappedBy=…)`) | "주인이 관리하는 그 FK 의 반대편" 임을 표시 | **무시** — 읽기 전용, SQL 생성 안 함 |
| **`mappedBy` 누락** | (지정 실패 → 별개 관계로 오해) | FK 에 쓰기 경로가 2개 → 불필요한 UPDATE 또는 조인 테이블 생성 |

> [!Caution]
> **"주인을 안 정한다" 는 선택지는 없다.** `@OneToMany` 에서 `mappedBy` 를 빼면 JPA 는 두 참조를 **별개의 관계 2개**로 오해해, `INSERT` 뒤에 불필요한 `UPDATE member SET dept_id=…` 가 더 나가거나 엉뚱한 조인 테이블을 만든다. 해법은 하나 — **FK 를 가진 쪽(`@ManyToOne`)을 주인으로 두고, 반대쪽엔 반드시 `mappedBy` 를 붙인다.**

### 연관관계 편의 메서드 — 양쪽을 한 번에 맞춘다

주인만 세팅하면 **DB 는 정확히 맞는다.** FK(`dept_id`)가 올바로 써지므로, 영속성 관점에선 이걸로 충분하다 — 실제로 주인만 세팅하고 끝내는 코드도 많다.

문제는 **메모리 쪽에서, 그것도 특정 조건에서만** 생긴다. 같은 영속성 컨텍스트 안에서 **이미 로딩해 둔** `dept.members` 컬렉션을, 회원을 바꾼 뒤 다시 읽을 때다. 한 번 메모리에 올라온 컬렉션은 Hibernate 가 자동으로 다시 읽지 않으므로, 거울을 안 맞춰주면 **옛 목록을 그대로** 보게 된다. (반대로 컬렉션이 아직 로딩 전이거나 새 트랜잭션이면, 다음 조회 때 DB 에서 새로 읽어 올바르게 보인다.)

그래서 편의 메서드는 **"항상 반드시" 가 아니라, 양방향 컬렉션을 같은 트랜잭션 안에서 탐색할 거라면 둬야 하는 안전장치**다. 양쪽 참조를 한 곳에서 같이 맞춰, 이 메모리 불일치를 애초에 빠뜨릴 수 없게 만든다.

```java
@Entity
public class Member {

    // 주인 쪽(Member)에 편의 메서드를 둔다
    public void changeDept(Department dept) {
        this.dept = dept;               // ① 주인 쪽 — FK 가 여기서 결정된다
        dept.getMembers().add(this);    // ② 거울 쪽 — 메모리 일관성을 맞춘다
    }
}
```

```java
// 호출부 — 한 줄로 양쪽이 동기화된다
member.changeDept(dept);
// 이제 member.getDept() 도, dept.getMembers() 도 서로를 올바로 가리킨다
```

> **핵심:** 양방향은 "참조가 둘" 이므로 **둘을 함께 세팅하지 않으면 메모리와 DB 가 어긋난다.** 편의 메서드는 그 두 줄을 **한 곳에 묶어** 빠뜨릴 수 없게 만드는 장치다.

> **편의 메서드 ⊂ 비즈니스 메서드.** 엔티티에 의미 있는 동작을 담는 게 비즈니스 메서드(`order.cancel()`, `member.changePassword()` …)이고, 편의 메서드는 그중 **목적이 "양방향 참조 동기화" 인 갈래**다. `changeDept` 처럼 "부서를 바꾼다(비즈니스)" + "양쪽을 맞춘다(편의)" 를 **겸하는** 경우가 많다.

> [!Note]
> **편의 메서드를 어디 두나 — 주인 여부와 무관하다.** "그 동작이 자연스러운 쪽 + 컬렉션을 가진 쪽" 에 둔다.
> - `회원이 부서를 바꾼다` → 회원의 단일 동작 → **`Member`**(주인) 에 `changeDept`
> - `글에 댓글을 추가/삭제한다` → 글이 거느린 컬렉션 관리 → **`Post`**(거울이어도!) 에 `addComment`/`removeComment`
>
> 위치가 주인이든 거울이든, **메서드 안에서 양쪽(주인 FK + 거울 컬렉션)을 다 세팅**한다는 점은 똑같다. (그래서 주인을 정하는 것과 편의 메서드를 어디 두는지는 **별개의 결정**이다)

---

### 양방향의 부작용 — 무한 순환

양방향이 되면 `Member` → `Department` → `members` → `Member` → … 로 **서로를 끝없이 참조**할 수 있다. 그래서 `toString()` 을 양쪽 연관까지 찍게 만들거나, 엔티티를 그대로 JSON 으로 직렬화하면 **무한 루프(StackOverflow)** 가 난다.

**① `toString()` 이 서로를 끝없이 부른다**

```java
@Entity
@Getter
@ToString                       // ← 모든 필드 포함 → dept 까지 찍는다
public class Member {
    private String name;
    private Department dept;     // toString() 안에서 dept.toString() 호출
}

@Entity
@Getter
@ToString                       // ← 모든 필드 포함 → members 까지 찍는다
public class Department {
    private String deptName;
    private List<Member> members;  // toString() 안에서 members(List).toString() 호출
}
```

`member.toString()` 을 부르는 순간:

```
member.toString()
  → dept.toString()                         // Member 의 dept 필드를 찍으려고
      → members.toString()                  // Department 의 members 필드 = List.toString()
          → (List 가 원소 순회) member.toString()   // 각 원소마다 ← 다시 처음으로!
              → dept.toString()
                  → ...  → 💥 StackOverflowError
```

포인트는 — **`members.toString()`(=`List.toString()`)이 내부에서 원소 하나하나의 `member.toString()` 을 부르기 때문에** 고리가 닫힌다. `List` 는 자기 원소들의 `toString()` 을 이어 부르는 통로인 셈이다.

**② 같은 함정 — JSON 직렬화**

네트워크는 자바 객체를 모른다. 메모리 속 `Member` 객체를 HTTP 로 내보내려면 **누구나 읽을 수 있는 텍스트(JSON)로 풀어내야** 하는데, 이 변환이 **직렬화(serialization)** 다. 우리 프로젝트에선 이 일을 **Jackson** 이 맡는다.

| 방향 | 이름 | 언제 |
| --- | --- | --- |
| 자바 객체 → JSON | **직렬화** (serialization) | 응답을 내보낼 때 |
| JSON → 자바 객체 | **역직렬화** (deserialization) | 요청(`@RequestBody`)을 받을 때 |

예를 들어 회원 `홍길동`(`test@donga.com`, 부서 `D011 비즈테크팀`) 한 명이 양방향으로 어떻게 오가는지 보면:

**직렬화 (객체 → JSON)**

| 자바 객체 | → | JSON |
| --- | --- | --- |
| `getName()` → `"홍길동"` | → | `"name": "홍길동"` |
| `getEmail()` → `"test@donga.com"` | → | `"email": "test@donga.com"` |
| `getDept().getDeptCode()` → `"D011"` | → | `"dept": { "deptCode": "D011",` |
| `getDept().getDeptName()` → `"비즈테크팀"` | → | `"deptName": "비즈테크팀" }` |

**역직렬화 (JSON → 객체)**

| JSON | → | 자바 객체 |
| --- | --- | --- |
| `"name": "홍길동"` | → | `name` 필드 ← `"홍길동"` |
| `"email": "test@donga.com"` | → | `email` 필드 ← `"test@donga.com"` |
| `"dept": { "deptCode": "D011", … }` | → | `new Department("D011", …)` 연결 |

```java
@GetMapping("/members/{id}")
public Member getMember(@PathVariable Long id) {
    return memberRepository.findById(id).orElseThrow();  // ❌ 엔티티 그대로 반환
}
```

Jackson(자바 객체 ↔ JSON 변환 라이브러리)이 `Member` 를 JSON 으로 바꾸면서 `dept` → `members` → 각 `member` → `dept` … 똑같이 무한 순환에 빠진다. (`StackOverflowError` 또는 `JsonMappingException: Infinite recursion`)

**③ 해결 — 한쪽 고리를 끊는다**

- `toString()` 에는 **연관 필드를 빼고** 자기 필드만 넣는다. (`@ToString(exclude = ...)`)

```java
@Entity
@Getter
@ToString(exclude = "dept")        // 연관 필드를 빼서 고리를 끊는다
public class Member { ... }

@Entity
@Getter
@ToString(exclude = "members")     // 컬렉션 쪽 통로를 막는다
public class Department { ... }
```

- JSON 순환도 `toString` 처럼 **annotation 으로 한쪽 고리를 끊을 수 있다.** 대표가 `@JsonIgnore` 다.

```java
@Entity
public class Member {
    @ManyToOne(fetch = FetchType.LAZY)
    private Department dept;
}

@Entity
public class Department {
    @JsonIgnore                    // 직렬화 때 이 필드를 통째로 제외 → dept→members 고리 끊김
    @OneToMany(mappedBy = "dept")
    private List<Member> members = new ArrayList<>();
}
```

| annotation | 동작 | 한계 |
| --- | --- | --- |
| **`@JsonIgnore`** | 한쪽 필드를 **직렬화에서 통째로 제외** | 그 필드를 **어떤 API 에서도 못 내보냄** |
| `@JsonManagedReference` / `@JsonBackReference` | 부모→자식만 직렬화, 자식→부모는 생략 | 짝을 맞춰야 하고 양방향 1쌍에만 |

> [!Caution]
> **`@JsonIgnore` 는 임시방편이다.** 엔티티에 "JSON 직렬화" 라는 **표현 계층 관심사**(= "이 데이터를 **화면·API 로 어떻게 보여줄까**" 라는 책임)를 **끌어들이는** 것이라 결합도가 올라가고, 한 번 무시하면 **화면마다 다른 응답**(이 화면엔 부서 포함, 저 화면엔 제외)을 만들 수 없다. 무엇보다 **엔티티는 DB 테이블과 매핑된 핵심 객체**라, 화면(API)의 요구사항에 엔티티가 휘둘려선 안 된다 — 응답 모양은 DTO 가 책임진다. 그래서 ↓ **DTO 반환이 정석**이다.

- API 응답은 엔티티를 직접 내보내지 말고 **전용 응답 객체(DTO)로 변환** 해서 내보낸다.

```java
public record MemberResponse(String name, String deptName) {
    public static MemberResponse from(Member m) {
        return new MemberResponse(m.getName(), m.getDept().getDeptName());
    }
}

@GetMapping("/members/{id}")
public MemberResponse getMember(@PathVariable Long id) {
    Member m = memberRepository.findById(id).orElseThrow();
    return MemberResponse.from(m);   // ✅ 엔티티가 아닌 DTO 반환 → 순환 원천 차단
}
```

> [!Note]
> **지금 당장 `@ToString(exclude)` 를 입력할 필요는 없다.** 우리 엔티티는 `@Getter` 만 있고 `@ToString` 이 없어서 — `toString()` 은 기본 구현(클래스명+해시)만 쓰고 연관을 찍지 않으므로 **순환이 생길 수 없다.** `@ToString(exclude)` 는 **`@ToString` 을 실제로 추가하는 그 순간** 함께 붙이면 된다. (오히려 더 자주 만나는 JSON 순환은 annotation 이 아니라 **DTO 반환**으로 막는 게 정석이다.)

#### 그럼 `@ToString` 은 언제 쓰나?

`@ToString` 은 **"기본으로 붙이는 것" 이 아니라, 그 객체를 로그·디버깅에서 사람이 읽을 일이 있을 때만** 붙이는 선택이다.

| 이슈                             | 결과                                          |
|--------------------------------|---------------------------------------------|
| **무한 순환**                      | 양방향 참조를 찍다 `StackOverflowError` (위에서 본 그것)  |
| **`LazyInitializationException`** | `toString()` 이 LAZY 연관을 건드리는데 트랜잭션 밖이면 터짐   |
| **숨은 쿼리·거대 로그**                | LAZY 를 초기화하며 추가 SQL 이 나가거나, 컬렉션 전체가 로그에 쏟아짐 |

그래서 기준을 이렇게 나눈다.

- **DTO·VO·요청/응답 객체 → 자유롭게 `@ToString`** — 연관 참조가 없고 로그에서 값 확인이 잦으니 오히려 권장.
- **엔티티 → 되도록 안 붙임. 꼭 필요하면 화이트리스트(`of`)로 단순 필드만 추가한다.**

```java
@Entity
@Getter
@ToString(of = {"id", "name"})   // 찍을 필드를 '지정' — 연관은 절대 안 들어감
public class Member { ... }
```

> [!Note]
> **상속받았다면 `callSuper`.** `@ToString` 은 기본적으로 **자기 필드만** 찍고 부모(`BaseEntity` 의 `createdAt` 등)는 뺀다. 부모 필드까지 찍으려면 `@ToString(callSuper = true)` — 단 **부모에도 제대로 된 `toString()` 이 있을 때만** (없으면 `BaseEntity@1a2b` 같은 해시가 끼어든다). (`@EqualsAndHashCode(callSuper = true)` 도 같은 개념)

> [!Caution]
> **`exclude`(블랙리스트)보다 `of`(화이트리스트)를 쓰자.** `exclude = "dept"` 는 지금은 안전해도, 나중에 누가 `@OneToMany List<Order> orders` 를 추가하면 **exclude 목록에 없으니 자동 포함 → 순환 함정이 부활**한다. `of = {"id", "name"}` 는 **새 연관이 추가돼도 지정한 것만 찍으므로 기본이 안전**하다.

> **한 줄 정리:** `@ToString` 은 "이 객체를 로그로 읽을 일이 있는가?" 가 yes 일 때 붙인다. DTO/VO 는 마음껏, 엔티티는 되도록 피하되 필요하면 `@ToString(of = {"id", …})` 로 **단순 필드만** 화이트리스트.

## 2단계. N+1 문제 — LAZY의 그림자

### 왜 N+1이 생기나

먼저 `LAZY` 와 `EAGER` 가 **로딩 시점**에서 어떻게 다른지부터 정리한다. (둘 다 N+1 자체를 푸는 도구는 아니다 — 시점만 다를 뿐이다.)

회원 목록을 뽑아 각자의 부서 이름을 찍는, 지극히 평범한 코드에서 시작한다.

```java
// ① 회원 전체 조회 — 쿼리 1번
List<Member> members = memberRepository.findAll();
//    실행 SQL:  SELECT * FROM member        ← 이때 각 member 의 dept 는 LAZY → 전부 "빈 상자(프록시)"

// ② 루프 돌며 각자의 부서 이름을 꺼냄
for (Member m : members) {
    System.out.println(m.getDept().getDeptName());  // ← 빈 상자를 '여는' 순간 → 부서 SELECT 한 번
}
```

| FetchType | 상태 | DB 조회 시점 |
| --- | --- | --- |
| `LAZY` | 프록시로 **대기** | 실제 값을 건드릴 때 |
| `EAGER` | 진짜 객체로 **즉시 로딩** | Member 를 가져올 때 (단, 목록 조회는 N번 나갈 수 있음) |

이 둘의 차이를 `Member`·`Department` 를 **상자**로 그려 보면 한눈에 들어온다. **LAZY = 라벨만 붙은 빈 상자(프록시), EAGER = 처음부터 꽉 찬 상자**다.

**LAZY — `Department` 는 "라벨(`id`)만 붙은 빈 상자(프록시)"**

```
① findById(member)  ─ 쿼리 1번:  SELECT * FROM member WHERE id=1

   Member (진짜 객체)              Department (프록시 = 빈 상자)
   ┌────────────────┐             ┌────────────────────┐
   │ id    : 1      │             │ id   : D011        │ ← 라벨(FK)만 있음
   │ name  : 홍길동  │ ──dept──▶  │ name :  ???        │ ← 속은 아직 비어 있음
   │ email : test   │             │(열기 전까지 DB 안 감)│
   └────────────────┘             └────────────────────┘
                                            │
② member.getDept().getDeptName()  ← 상자를 "여는" 순간
                                            ▼
        ─ 쿼리 또 1번:  SELECT * FROM department WHERE id='D011'
                                            ▼
                                  ┌────────────────────┐
                                  │ id   : D011        │
                                  │ name : 비즈테크팀    │ ← 그제서야 채워짐
                                  └────────────────────┘
```

**EAGER — `Department` 는 "처음부터 꽉 찬 상자"**

```
① findById(member)  ─ 쿼리 1번에 JOIN 으로 둘 다:

   SELECT m.*, d.*  FROM member m  JOIN department d  ON m.dept_id = d.id

   Member (진짜 객체)              Department (진짜 객체, 이미 채워짐)
   ┌────────────────┐             ┌────────────────────┐
   │ id    : 1      │             │ id   : D011        │
   │ name  : 홍길동  │ ──dept──▶  │  name : 비즈테크팀   │← 처음부터 값이 있음
   │ email : test@. │             │                    │
   └────────────────┘             └────────────────────┘

② member.getDept().getDeptName()  ← 이미 차 있으니 추가 쿼리 없음
```

> **여기서 N+1 로 이어진다.** 회원이 100명이면, LAZY 에서 각 회원의 `dept` 상자를 하나씩 열 때마다 SELECT 가 한 번씩 나가 — **빈 상자 100개를 100번 열어 100번 쿼리**. 이게 곧 N+1 의 정체다. (EAGER 로 바꿔도 목록 조회 땐 상자를 100번 따로 채우려 들어 똑같이 터진다.)



**왜 "1 + N" 인가?**

- **1** = ①의 회원 목록 조회(`SELECT * FROM member`) — 딱 한 번.
- **N** = ②에서 회원 한 명의 `getDept().getDeptName()` 을 부를 때마다, 그 빈 상자(프록시)를 채우려 부서 SELECT 가 한 번씩. 회원이 100명이면 부서 쿼리 100번.

`show-sql` 로 보면 이렇게 **N번 찍히는 걸 직접 눈으로** 확인할 수 있다.

```
SELECT * FROM member;                       ← 1  (목록)
SELECT * FROM department WHERE id='D011';   ← 2  (1번째 회원의 dept)
SELECT * FROM department WHERE id='D012';   ← 3  (2번째 회원의 dept)
SELECT * FROM department WHERE id='D013';   ← 4  (3번째 회원의 dept)
...                                            (100번째까지)
= 총 1 + 100 = 101번
```

> [!Note]
> **딱 101번은 "100명의 부서가 전부 다를 때" 의 최악의 경우이다.** 같은 트랜잭션 안에선 **1차 캐시**가 작동해, 이미 조회한 부서(`D011`)는 다시 쿼리하지 않는다. 그래서 실제 N 은 **"서로 다른 부서의 개수"** 에 가깝다 — 모두 같은 부서면 `1 + 1 = 2`번, 10개 부서에 흩어져 있으면 `1 + 10 = 11`번. 다만 실무에선 제각각인 경우가 많아, **"최악은 1+N"** 으로 잡아두는 게 안전하다.

### ⚠️ EAGER는 답이 아니다

"그럼 `fetch = EAGER` 로 바꾸면 되지 않나?" 싶을 수 있다. 하지만 EAGER 는 **더 나쁘다** — 항상·모든 곳에서 조인이 끌려와 통제 불가, 페이징·성능 문제를 부른다.

> **결론:** 기본은 LAZY 로 두고, **필요할 때만 명시적으로 당겨오는** 게 정석이다 → 3단계.

## 3단계. Fetch Join — 한 방에 같이 가져오기

### JOIN FETCH 문법

N+1 의 원인은 "**부서를 나중에, 한 명씩 따로 가져오는 것**" 이었다. 그렇다면 해법은 단순하다 — **회원을 조회하는 그 쿼리에서 부서까지 같이 끌고 오면** 된다. 그걸 JPQL 로 지시하는 게 `JOIN FETCH` 다.

**Before — N+1 나던 코드**

```java
// 평범한 findAll → dept 는 LAZY(빈 상자)
List<Member> members = memberRepository.findAll();
for (Member m : members) {
    m.getDept().getDeptName();   // ← 상자 열 때마다 부서 SELECT
}
```

```
SELECT * FROM member;                       ← 1
SELECT * FROM department WHERE id=?;        ← + N  (회원 수만큼)
= 1 + N
```

> [!Caution]
> **여기서 — "`fetch` 타입을 바꾸면 되지 않나?"** 안 된다. 위 코드는 이미 `FetchType.LAZY` 이고, **LAZY 라서 N+1 이 나는** 것이다. 그렇다고 `EAGER` 로 바꿔도 목록 조회에선 부서를 건별로 채워 똑같이 N+1 이 난다.
>
> 이유는 **`LAZY`/`EAGER` 는 "언제 가져올까(시점)" 만 정할 뿐, "몇 번에 나눠 가져올까(쿼리 수)" 는 못 정하기 때문**이다. 둘 다 부서를 **한 건씩** 가져온다.
>
> | | 무엇을 정하나 | N+1 을 푸나 |
> | --- | --- | --- |
> | `LAZY` | 부서를 **나중에** | ❌ 원인 그 자체 |
> | `EAGER` | 부서를 **즉시** | ❌ 목록에선 똑같이 N+1 |
> | **Fetch Join** | "이번 쿼리는 부서까지 **JOIN 한 방에**" | ✅ 쿼리를 **1번**으로 합침 |
>
> 그래서 **fetch 타입 종류가 아니라, 쿼리 레벨(Fetch Join)에서** 풀어야 한다.

---

**After — `JOIN FETCH` 로 부서를 함께 로딩**

```java
@Query("SELECT m FROM Member m JOIN FETCH m.dept")
List<Member> findAllWithDept();
```

```
SELECT m.*, d.*
FROM member m
JOIN department d ON m.dept_id = d.id;   ← 딱 1번 (부서까지 채워서 옴)
```

루프에서 `m.getDept().getDeptName()` 을 불러도 **추가 쿼리가 안 나간다.** 이미 부서가 진짜 객체로 채워져 왔기 때문이다. `1 + N` → **1**.

> **왜 그냥 `JOIN` 이 아니라 `JOIN FETCH` 인가?** 이게 핵심이다.

| | 일반 `JOIN` | `JOIN FETCH` |
| --- | --- | --- |
| SQL 에 조인 | O | O |
| **연관 엔티티를 영속성 컨텍스트에 채우나** | ❌ (조건/필터용으로만 씀) | ✅ (진짜 객체로 로딩) |
| 조인했는데 `getDept()` 하면 | 여전히 **프록시 → 또 쿼리(N+1 그대로)** | 이미 차 있음 → **추가 쿼리 없음** |

> 즉 일반 `JOIN` 은 "조인은 했지만 부서는 안 담아온다" — SQL 만 조인이고 객체는 그대로 빈 상자다. **`FETCH` 키워드가 "조인한 그 부서를 객체에 실제로 채워라" 를 지시**하는 것이고, 그래야 N+1 이 사라진다.

**"연관 엔티티를 영속성 컨텍스트에 채운다" 가 정확히 뭔가?** — 부서를 **진짜 객체로 만들어 1차 캐시(영속성 컨텍스트)에 올려둔다**는 뜻이다. 그래야 이후 `getDept()` 가 **추가 쿼리 없이** 바로 값을 돌려준다. 핵심은 **`SELECT` 절에 무엇이 따라오느냐** 다 — JPQL 은 `SELECT` 한 것만 객체로 채워온다.

반대로 일반 `JOIN` 은 연관을 **"조건/필터" 로만** 쓸 때 쓴다. 예를 들어 "비즈테크팀 소속 회원만" 거를 때:

```java
// 부서로 '거르기'만 한다 — 부서 자체는 결과로 안 가져온다
@Query("SELECT m FROM Member m JOIN m.dept d WHERE d.deptName = '비즈테크팀'")
List<Member> findSalesMembers();
```

```sql
SELECT m.*  FROM member m  JOIN department d ON m.dept_id = d.id
WHERE d.dept_name = '비즈테크팀'        ← SELECT 절엔 m 만 → dept 는 안 채움(프록시 그대로)
```

`SELECT m` 이라 **회원만** 객체로 채워지고, `dept` 는 거르는 데만 쓰이고 버려진다. 그래서 이후 `getDept()` 하면 또 쿼리가 나간다. 부서까지 채우려면 **`SELECT` 절에 부서가 따라오도록 `FETCH` 를 붙여야** 한다 → 그게 `JOIN FETCH`.

> [!Note]
> **참고) @EntityGraph — 같은 효과를 애너테이션으로**
>
> Fetch Join 과 **같은 일(연관을 함께 로딩)** 을, JPQL 을 적지 않고 애너테이션만으로 낼 수 있다.
> 특히 `findAll`·`findById` 처럼 **우리가 쿼리를 못 적는 기본 제공 메서드**나 쿼리 메서드 위에 얹을 때 유용하다.
>
> ```java
> // JPQL 로 fetch join 을 쓰는 대신
> @Query("SELECT m FROM Member m JOIN FETCH m.dept")
> List<Member> findAllWithDept();
>
> // 애너테이션만으로 같은 효과. 상속받은 findAll 을 그대로 두고 'dept 를 함께' 만 선언
> @EntityGraph(attributePaths = {"dept"})
> List<Member> findAll();
> ```
>
> **언제 무엇을:** 단순히 "같이 가져오기" 만이면 `@EntityGraph`, 조건·정렬·조인이 복잡하면 Fetch Join(JPQL).
> (단 `@EntityGraph` 는 항상 LEFT OUTER JOIN 이고, 컬렉션이면 Fetch Join 과 똑같은 페이징 함정을 가진다.)

> [!Note]
> **참고) QueryDSL — 타입 안전한 코드로 fetch join**
>
> JPQL 문자열 대신 **컴파일 타임에 검증되는 코드**로도 같은 fetch join 을 낸다. 핵심은 `.fetchJoin()` 한 줄이다.
>
> ```java
> List<Member> result = queryFactory
>      .selectFrom(member)
>      .join(member.dept).fetchJoin()   // ← JPQL 의 JOIN FETCH 와 같은 일
>      .fetch();
> ```
>
> - `.join(member.dept)` **만** → 일반 JOIN (dept 안 채움 = 위 표의 ❌)
> - `.fetchJoin()` **까지** → JOIN FETCH (dept 까지 진짜 객체로 로딩 = ✅)
>
> 즉 QueryDSL 도 "조인" 과 "fetch" 를 **분리**해 표현한다 — JPQL 의 `JOIN` vs `JOIN FETCH` 와 정확히 대응한다.

### 향후 추가 교육예정

`N:1` 같은 **단건** 연관(`Member → Department`)은 Fetch Join 한 방이면 끝이고 함정이 없다. 그런데 방향이 반대인 **컬렉션(`1:N`)** — `Department → List<Member>` 처럼 "하나에 여럿" 을 Fetch Join 하는 순간, **단건엔 없던 문제 세 가지**가 새로 생긴다.

| 함정 | 한 줄 | 해결 |
| --- | --- | --- |
| **중복 row** | 자식 수만큼 부모 행이 복제됨 | `DISTINCT` (※ Hibernate 6 / Spring Boot 3.x 부터는 엔티티 조회 시 자동 중복 제거) |
| **페이징 깨짐** | 행 뻥튀기로 DB 페이징 불가 → 메모리 페이징 → `OutOfMemoryError` 위험 | `hibernate.default_batch_fetch_size` 또는 `@BatchSize` |
| **컬렉션 둘 금지** | 컬렉션 2개 Fetch Join → 카테시안 곱 → `MultipleBagFetchException` | 하나만 Fetch Join, 나머지는 `@BatchSize` |

> 셋 다 **`1:N` 컬렉션** 이야기다. 이번 주(본편)는 `N:1` 까지만 다루므로 여기선 **"이런 게 있다" 만 예고**하고, 실제 재현 코드와 해결(`DISTINCT`·`@BatchSize`)은 향후에 다룬다.

## 다음 — 또 다른 조회 전략들

N+1 의 해결책은 Fetch Join 하나가 아니다. 0단계에서 깔아둔 **세 갈래** 중 나머지 둘 — **DTO 프로젝션**과 **OSIV** — 그리고 "언제 무엇을 쓸지" 의 **선택 기준**은 **다음 주차** 에서 본편 주제로 다룬다.

| 전략 | 한 줄 | 트레이드오프 |
| --- | --- | --- |
| **DTO 프로젝션** | 필요한 컬럼만 뽑아 **엔티티를 아예 안 만든다** → 프록시·N+1 원천 차단 | 영속 객체가 아니라 **변경 감지 안 됨**(읽기 전용) |
| **OSIV** | 요청 끝까지 영속성 컨텍스트를 **살려둔다** → 컨트롤러/뷰의 LAZY 도 안 터짐 | DB 커넥션을 **요청 내내 점유** → 성능·확장성 부담 |
| **선택 기준** | 수정 흐름 → 엔티티 + Fetch Join, 읽기 전용 목록 → DTO | — |
