# JPA `ddl-auto` 옵션 정리

`spring.jpa.hibernate.ddl-auto` 는 애플리케이션이 시작·종료될 때 Hibernate가 테이블을 어떻게 다룰지 정하는 설정입니다.

## 옵션별 동작

| 값 | 시작할 때 | 끝날 때 | 데이터 |
|---|---|---|---|
| `create` | drop 후 create | 그대로 둠 | 시작 시마다 초기화 |
| `create-drop` | drop 후 create | **drop** | 시작 초기화 + 종료 시 삭제 |
| `update` | 없으면 만들고, 바뀐 것만 반영 | 그대로 둠 | **유지됨** |
| `validate` | 엔티티 ↔ 테이블 일치만 검사 (생성 X) | — | 유지됨 |
| `none` | 아무것도 안 함 | — | 유지됨 |

> `create` 와 `create-drop` 의 차이는 인메모리 DB에서는 거의 드러나지 않습니다.
> 앱이 꺼지면 메모리 DB 자체가 사라지기 때문입니다. 차이는 file 모드나 MySQL처럼
> 데이터가 디스크에 남는 경우에 나타납니다.

## 환경별로 주로 쓰는 값

### 개발 / 학습 단계
- **`create` 또는 `create-drop`** — 엔티티를 자주 바꾸므로 매번 깨끗하게 새로 만드는 게 편합니다.
  매핑 변경이 즉시 반영됩니다. (인메모리 H2 + 학습용으로 가장 흔함)
- **`update`** — 개발 중에도 데이터를 살려두고 싶을 때. 단, 컬럼 추가는 해주지만
  **컬럼 삭제·타입 변경은 제대로 반영하지 못하는** 한계가 있습니다.
  "분명 엔티티를 고쳤는데 반영이 안 되는" 현상의 원인이 되곤 합니다.

### 테스트(통합 테스트) 단계
- **`create-drop`** — 테스트가 끝나면 테이블까지 정리되어 깔끔합니다.
  테스트마다 동일한 초기 상태를 보장하기 좋습니다.

### 운영(Production) 단계
- **`validate`** — 엔티티와 실제 테이블 구조가 일치하는지 검증만 하고,
  스키마는 절대 건드리지 않습니다. 가장 안전한 운영 기본값입니다.
- **`none`** — 검증조차 하지 않음. 스키마 변경은 Flyway·Liquibase 같은
  **마이그레이션 도구로 따로 관리**할 때 사용합니다.

> ⚠️ 운영에서는 `create` / `create-drop` 절대 금지.
> 배포할 때마다 실데이터가 통째로 삭제됩니다.
> 스키마 변경은 마이그레이션 도구(Flyway, Liquibase)로 버전 관리하는 것이 원칙입니다.
