## 0단계. 지난주 복습 — 우리는 "엔티티"를 생성했다.

3주차에 우리는 `Member`, `Department`, `Post` … 같은 **엔티티(객체 ↔ 테이블 매핑)** 를 정의했다.
그런데 정작 이 엔티티를 **DB에 저장하거나 조회하는 코드**는 아직 한 줄도 작성하지 않았다.

그 일을 담당하는 계층이 바로 이번 주 주제인 **Repository** 다.
그리고 Repository가 어떻게 동작하는지 이해하려면,  **영속성 컨텍스트**부터 봐야 한다.

> 3주차 자료(3페이지)에서 "1차 캐시 / 변경 감지는 향후 설명"이라고 미뤄뒀던 그 내용에 대해 설명한다.

## 1단계. 영속성 컨텍스트 — JPA의 심장

### 영속성 컨텍스트란?

**왜 이런 게 필요할까?** JDBC 시절엔 SQL 이 코드에 직접 박혀 있어서, 객체를 하나 바꾸면 매번 손으로 `UPDATE ... SET ...` 을 짜야 했다. JPA 는 **객체 세계와 DB 세계 사이에 "완충 지대"** 를 두기로 했고, 그게 바로 영속성 컨텍스트다.
이 완충 지대 덕에 우리는 **객체만 만지면 되고, SQL 은 JPA 가 알아서 만들어준다** — 그 "알아서 만들어주는" 정체가 바로 아래 세 가지 메커니즘이다.

한 줄로: **"엔티티를 보관하는 가상의 DB, 트랜잭션 동안만 살아 있는 임시 저장소"** 다.

우리가 `repository.save(member)` 를 호출하면, JPA는 바로 DB에 INSERT를 날리는 게 **아니다**.
일단 이 **영속성 컨텍스트라는 상자 안에 엔티티를 넣어두고 관리**한다.
그리고 이 상자가 제공하는 세 가지 있다  
**1차 캐시 / 쓰기 지연 / 변경 감지**.

### 엔티티의 4가지 상태

| 상태 | 의미 | 예 |
| --- | --- | --- |
| 비영속 (transient) | `new` 로 막 만든, 아직 상자 밖 객체 | `Member m = new Member(...)` |
| 영속 (managed) | 영속성 컨텍스트가 관리 중 | `repository.save(m)` 호출 후, `findById` 로 꺼낸 직후 |
| 준영속 (detached) | 관리받다가 상자 밖으로 나옴 (트랜잭션 종료 등) | 트랜잭션이 끝난 뒤의 그 객체 |
| 삭제 (removed) | 삭제 예약됨 | `repository.delete(m)` 호출 후 |

> **이번 주 내내 가장 중요한 구분은 "영속 vs 준영속"** 이다.
> 
> **변경 감지**는 영속 상태에서만 작동하고, **LazyInitializationException**은 준영속 상태에서 터진다.


### 영속성 컨텍스트를 다루는 메서드 — persist / flush / clear

위 상태들 **사이를 옮기는 동작**이 `EntityManager` 의 메서드다. 예제에서 자주 나오는데 헷갈리기 쉬운 셋을 정리한다.

| 메서드 | 하는 일 | 상태 변화 | DB에 즉시? |
| --- | --- | --- | --- |
| `persist(e)` | 객체 **하나**를 상자에 **등록**(영속화). INSERT를 예약 | 비영속 → 영속 | ✕ (보통 지연)¹ |
| `flush()` | 상자에 쌓인 변경(INSERT·UPDATE·DELETE)을 **DB로 전송**(동기화) | 변화 없음 | ○ |
| `clear()` | 상자를 **통째로 비움**. 안에 있던 영속 객체가 전부 떨어져 나감 | 영속 → 준영속(전부) | ✕ |

> ¹ 단, `IDENTITY` 전략은 id를 받아오려고 `persist` 시점에 INSERT가 즉시 나간다. (아래 (2) 참고)

영속성 컨텍스트를 **"객체 상자"** 라고 보면 셋의 차이가 분명해진다.

- **`persist`** = 객체를 **상자에 넣기** (이제부터 JPA가 관리)
- **`flush`** = 상자에 쌓인 변경을 **DB에 실제로 반영하기** (상자는 그대로 둠)
- **`clear`** = 상자를 **통째로 비우기** (DB 반영과 무관, 안의 객체를 전부 손에서 놓음)

**헷갈리지 말 것 — 셋은 서로 독립이다.**

- `flush ≠ commit` : flush는 SQL만 보낼 뿐 트랜잭션은 안 끝난다. (이 상태에서 롤백하면 되돌아감)
- `flush ≠ clear` : flush해도 객체는 상자에 **그대로 남는다.** 비우는 건 `clear` 다.
- `persist` 했다고 DB에 바로 가는 것도, `flush` 했다고 상자가 비는 것도 아니다.

> **`save()` 와의 관계:** `repository.save()` 는 새 엔티티면 내부에서 `persist` 를 부른다.
> 이미 영속 상태인 엔티티면 변경 감지에 맡기므로 사실상 추가 동작이 없다. (2단계에서 다시 봄)
>
> **`clear()` 를 왜 쓰나:** 1차 캐시·변경 감지를 **테스트**할 때, "DB에 진짜 반영됐는지" 확인하려면
> 상자를 비워 **강제로 DB에서 다시 읽게** 만들어야 하기 때문이다. (실무 서비스 코드에서 직접 부를 일은 드물다)


### (1) 1차 캐시 — 같은 트랜잭션 안에서는 DB를 다시 안 간다

**왜 캐시를 두나?** 1차 캐시는 "성능을 위한 캐시" 라기보단, **변경 감지·쓰기 지연이 동작할 토대**다.
JPA 가 엔티티를 *관리* 하려면 어딘가에 들고 있어야 하고, 그 보관소가 바로 1차 캐시다. 부수적으로 두 효과가 따라온다 — **같은 PK 의 중복 조회 안 함** + **객체 동일성 보장(`==`)**.

```java
Member m1 = memberRepository.findById(1L).get(); // ① DB 조회 → 상자에 보관
Member m2 = memberRepository.findById(1L).get(); // ② DB 안 감! 상자에서 그대로 반환

System.out.println(m1 == m2); // true — 같은 객체임이 보장된다
```

같은 트랜잭션 안에서 같은 PK를 두 번 조회하면, 두 번째는 SQL이 나가지 않는다.
이미 상자에 들고 있으니 그걸 돌려줄 뿐이다. (그래서 `m1 == m2` 가 `true`)

> **객체 동일성(`==`)이 왜 중요한가:** 만약 두 번의 조회가 서로 *다른* 객체를 돌려준다면, 한쪽에서 `changeName("A")` 하고 다른 쪽에서 `changeName("B")` 했을 때 **변경 감지가 어느 쪽을 기준으로 UPDATE 해야 할지** 알 수 없다.
> 같은 트랜잭션 안에선 같은 객체임이 보장돼야 변경 감지가 안전하게 동작한다. → **1차 캐시는 변경 감지의 전제조건**이다.

### (2) 쓰기 지연 — save 시점 ≠ DB 반영 시점(flush)

```java
@Transactional
void example() {
    Member member = memberRepository.findById(1L).orElseThrow();
    member.changeName("새이름");   // 변경 내용을 일단 상자에만 기록 (UPDATE 즉시 안 나감)
    // ...
}   // 트랜잭션 끝(commit) → flush → 이때 비로소 실제 SQL이 DB로 나간다
```

`save()` 나 값 변경의 시점이 곧 **DB 반영 시점은 아니다.**
JPA는 바뀐 내용을 **상자(쓰기 지연 저장소)에 모아뒀다가**, **flush** 라는 순간에 실제 SQL로 내보낸다.
flush는 보통 **트랜잭션이 끝날 때(commit)** 자동으로 일어난다.

> **왜 즉시 안 보내고 굳이 모았다가 보낼까?** 이유는 셋이다.
> ① **변경 감지를 가능하게 하기 위해** — 즉시 보내버리면 "원본 ↔ 현재" 를 비교할 시점이 사라진다. 모아둬야 다음 (3) 의 마법이 가능하다.
> ② **롤백이 자연스러워진다** — 아직 안 보낸 SQL 은 롤백할 일도 없다. 트랜잭션이 실패하면 그냥 안 보내면 끝.
> ③ **성능** — 같은 트랜잭션의 SQL 을 모아 한 번에 보내면 DB 왕복 비용이 줄어든다.
>
> 즉 **"flush = 진짜 반영 시점"** 개념이 바로 다음 (3) 변경 감지의 토대다 — 값을 바꿔도 flush 시점까지 모아두기 때문에 비교·자동 UPDATE 가 가능하다.

> **참고(심화) — INSERT는 예외가 있다.**
> `@GeneratedValue(strategy = IDENTITY)`(우리 `Member` 가 이 방식)는 id를 **DB가 INSERT 순간에** 매긴다.
> JPA는 id가 있어야 엔티티를 상자에 보관할 수 있는데, 그 id를 알아낼 방법이 INSERT 실행뿐이라
> **`save()` 시점에 INSERT가 곧장 나간다(지연 안 됨).** "INSERT를 모았다 한 번에"는 `SEQUENCE` 전략에서만 성립한다.
> 반면 **UPDATE/DELETE는 전략과 무관하게 항상 flush까지 지연**되므로, 쓰기 지연의 대표 예시는 INSERT가 아니라 UPDATE로 잡는 게 정확하다.

### (3) 변경 감지(Dirty Checking) — UPDATE 코드가 사라진다

이게 처음 보면 가장 신기한 부분이다.

```java
@Transactional
public void changeName(Long id, String newName) {
    Member member = memberRepository.findById(id).orElseThrow();
    member.changeName(newName);   // 값만 바꿨다
    // memberRepository.save(member);  ← 이 줄을 안 적어도 된다!
}
// 트랜잭션이 끝나면 JPA가 알아서 UPDATE SQL을 실행한다
```

**왜 `save()` 를 안 불렀는데 UPDATE가 나갈까?**
영속성 컨텍스트는 엔티티를 처음 들여올 때의 **원본 스냅샷**을 함께 보관한다.
트랜잭션이 끝나는 flush 시점에 **현재 값 ↔ 스냅샷**을 비교(이것이 "변경 감지")해서,
달라진 게 있으면 **자동으로 UPDATE SQL을 만들어 보낸다.**

> **핵심:** "조회한 엔티티의 값을 바꾸면, 트랜잭션 안에서는 그것만으로 DB에 반영된다."
> JDBC 시절 `UPDATE ... SET ...` 을 손으로 짜던 일이 사라지는 지점이다.

### 트랜잭션 경계 — @Transactional 이 영속성 컨텍스트의 수명이다

여기까지의 모든 마법(1차 캐시·쓰기 지연·변경 감지)은 **하나의 전제** 위에 있다.

> **영속성 컨텍스트는 트랜잭션과 생사를 같이한다.**
> `@Transactional` 이 시작될 때 태어나고, 끝날 때 flush 후 사라진다.

```java
@Service
public class MemberService {

    @Transactional                     // ← 여기서 영속성 컨텍스트가 살아난다
    public void updateMember(Long id) {
        Member member = memberRepository.findById(id).orElseThrow(); // 영속 상태
        member.changeName("새이름");      // 변경 감지 대상이 됨
    }                                  // ← 메서드 끝 = 트랜잭션 끝 = flush(UPDATE) + 컨텍스트 소멸
}
```

> **Caution**
> `@Transactional` 이 **없으면** 변경 감지가 동작하지 않는다.
> "분명 값을 바꿨는데 DB에 반영이 안 돼요" 사고의 가장 흔한 원인이다.
> 데이터를 **바꾸는** 서비스 메서드에는 `@Transactional` 을 붙이는 것이 기본이다.
> (조회만 하는 메서드에는 `@Transactional(readOnly = true)` 를 붙이는 것이 관례 — 성능 이점이 있다)

> 단, 변경 감지에도 약점이 하나 있다 — **다루는 데이터 수가 많아지면 독이 된다.** 이 얘기는 `@Query` 까지 본 뒤, 5단계에서 `@Modifying` 과 함께 한꺼번에 짚는다.

## 2단계. Repository 기초 — JpaRepository

이제 토대를 깔았으니, 실제로 저장/조회하는 도구를 본다.

### 인터페이스만 만들면 구현체는 Spring이 준다

```java
public interface MemberRepository extends JpaRepository<Member, Long> {
}
//                                          ↑          ↑
//                                     엔티티 타입    PK 타입
```

이게 끝이다. **구현 클래스를 우리가 안 짠다.**
인터페이스만 선언하면 Spring Data JPA가 런타임에 구현체(프록시)를 자동으로 만들어 주입해 준다.

### 기본으로 제공되는 메서드

별도로 한 줄도 안 적었는데, 아래가 전부 공짜로 따라온다.

| 메서드 | 역할 |
| --- | --- |
| `save(entity)` | 저장 또는 수정 (아래 설명) |
| `findById(id)` | PK로 단건 조회 → **`Optional`** 로 감싸서 반환 |
| `findAll()` | 전체 조회 |
| `delete(entity)` / `deleteById(id)` | 삭제 |
| `count()` | 개수 |
| `existsById(id)` | 존재 여부 (boolean) |

### save() 하나가 INSERT도 되고 UPDATE도 되는 이유

```java
Member member = new Member("홍길동", "hong@test.com", dept);
memberRepository.save(member);   // id가 없으니 → INSERT

Member found = memberRepository.findById(1L).orElseThrow();
found.changeName("김길동");
memberRepository.save(found);    // 사실 이 save는 없어도 된다 (변경 감지!)
```

`save()` 는 내부적으로 **엔티티가 새것인지(식별자가 없는지)** 를 보고 INSERT/UPDATE를 결정한다.
하지만 **이미 영속 상태인 엔티티는 값만 바꿔도 변경 감지로 UPDATE** 되므로,
조회 후 수정 시 `save()` 를 다시 부르는 건 사실 불필요하다. (1단계 변경 감지와 연결되는 지점)

## 3단계. Optional — `findById` 가 돌려주는 상자

### 왜 Member 가 아니라 Optional\<Member\> 인가

```java
Optional<Member> result = memberRepository.findById(1L);
```

`findById` 는 `Member` 가 아니라 `Optional<Member>` 를 돌려준다.
**조회 결과가 없을 수도 있기 때문**이다. (없는 PK를 조회하면?)

JDBC 시절엔 결과가 없으면 `null` 이 돌아왔고, 그걸 깜빡 체크 안 하면 `NullPointerException` 이 터졌다.
`Optional` 은 **"이 안에 값이 없을 수도 있다"는 사실을 타입으로 강제**해서, 호출하는 쪽이 빈 경우를 반드시 다루게 만든다.

### Repository 계층의 관용구 — orElseThrow

가장 많이 쓰는 소비 패턴은 이 한 줄이다. **통째로 외워두자.**

```java
Member member = memberRepository.findById(id)
        .orElseThrow(() -> new MemberNotFoundException(id));
```

"있으면 꺼내고, 없으면 예외를 던져라."
조회 대상이 당연히 있어야 하는 상황(상세 조회 등)에서 이 패턴이 표준이다.

값이 없을 때 예외 대신 **기본값**을 주고 싶다면:

```java
Member member = memberRepository.findById(id)
        .orElse(Member.guest());   // 없으면 게스트 회원 반환
```

### ⚠️ 안티패턴 두 가지

```java
// ❌ ① 무지성 .get() — 값이 없으면 NoSuchElementException. Optional 쓰는 의미가 사라진다.
Member member = memberRepository.findById(id).get();

// ❌ ② isPresent() 후 .get() — if문이 부활. Optional 도입 취지가 무색해진다.
Optional<Member> opt = memberRepository.findById(id);
if (opt.isPresent()) {
    Member member = opt.get();
    // ...
}
```

둘 다 "null 체크의 다른 이름"일 뿐이다. `orElseThrow` / `orElse` / `map` 으로 **꺼내지 않고 처리**하는 게 핵심.

> Optional은 더 깊은 철학(필드로 쓰지 마라, 파라미터로 쓰지 마라 등)이 있지만,
> 이번 주는 **"Repository 결과를 안전하게 꺼내 쓰는 법"** 까지만 다룬다.

## 4단계. 쿼리 메서드 — 메서드 이름이 곧 쿼리

PK가 아닌 다른 조건으로 조회하고 싶을 때, **메서드 이름만 규칙대로 지으면** Spring이 쿼리를 만들어 준다.

### 동작 원리

```java
public interface MemberRepository extends JpaRepository<Member, Long> {

    Optional<Member> findByEmail(String email);
    //               └──┬──┘ └──┬──┘
    //                동작     조건 필드
    // → SELECT * FROM member WHERE email = ?

    List<Member> findByDept(Department dept);     // 부서로 회원 목록 조회
    List<Member> findByNameContaining(String kw); // 이름에 kw 포함 (LIKE)
    boolean existsByEmail(String email);          // 존재 여부
}
```

메서드 이름의 키워드를 Spring이 파싱해서 JPQL → SQL로 번역해 준다. **구현은 역시 안 짠다.**

### 자주 쓰는 키워드

| 키워드 | 예시 | 의미 |
| --- | --- | --- |
| `And` / `Or` | `findByNameAndEmail` | 조건 결합 |
| `Containing` | `findByNameContaining` | LIKE `%kw%` |
| `GreaterThan` / `LessThan` | `findByAgeGreaterThan` | 비교 |
| `Between` | `findByAgeBetween` | 범위 |
| `OrderBy` | `findByDeptOrderByNameAsc` | 정렬 |
| `In` | `findByIdIn` | IN 절 |

### 한계 — 이름이 길어지면 진다

```java
// 😵 조건이 늘어날수록 메서드 이름이 읽기 불가능해진다
List<Member> findByNameAndEmailAndDeptAndAgeGreaterThanOrderByCreatedAtDesc(...);
```

이쯤 되면 메서드 이름만 봐서는 무슨 쿼리인지 알 수 없다. 이때 다음 단계의 `@Query` 로 넘어간다.

## 5단계. @Query — JPQL 직접 작성

### JPQL은 "테이블"이 아니라 "엔티티"를 조회한다

```java
@Query("SELECT m FROM Member m WHERE m.email = :email")
Optional<Member> findByEmailJpql(@Param("email") String email);
```

언뜻 SQL과 비슷해 보이지만 다르다.

- SQL: `SELECT * FROM member` → **테이블 `member`** 를 조회
- JPQL: `SELECT m FROM Member m` → **엔티티 `Member` 클래스** 를 조회 (`m.email` 은 컬럼이 아니라 **필드**)

> 3주차에서 배운 **패러다임 불일치 해결**의 연장선이다.
> 우리는 테이블이 아니라 **객체를 대상으로** 쿼리하고, JPA가 그걸 실제 SQL로 번역한다.

### 언제 @Query 를 쓰나 — 판단 기준

조건 개수 같은 **숫자로 선을 긋지 않는다.** 기준은 **가독성·의도**다.

> **"메서드 이름이 한눈에 안 읽히기 시작하면, @Query 로 옮긴다."**

- 메서드 이름이 너무 길어 의미 파악이 어려울 때
- 조인이 필요할 때
- 특정 컬럼/DTO만 골라 조회하고 싶을 때

### ⚠️ JPQL의 함정 — 오타는 런타임에 터진다

```java
@Query("SELECT m FROM Member m WHERE m.emial = :email")  // 'emial' 오타!
Optional<Member> findByEmail(@Param("email") String email);
```

이 오타는 **컴파일 시점에 안 잡힌다.** 문자열이기 때문이다.
앱을 띄우거나 그 메서드를 호출하는 **런타임에 가서야** 터진다.
쿼리 메서드(`findBy...`)도 마찬가지로 필드명이 틀리면 실행 시점에 실패한다.

> 그래서 **JPQL/쿼리 메서드를 작성하면 반드시 테스트로 한 번 실행해 보는 습관**이 중요하다.
> (문자열 쿼리의 이 약점을 컴파일 타임에 잡아주는 **QueryDSL** 같은 도구가 있는데, 그건 동적 쿼리와 함께 별도 주차에서 다룬다.)

### ⚠️ 변경 감지의 맹점 — 대량 처리

여기까지 본 `@Query` 는 전부 SELECT 였다. 그런데 `@Query` 로 **UPDATE/DELETE 를 쓸 일도 생기는데, 그 동기**가 1단계에서 미뤄둔 이야기에 있다.
**1단계의 변경 감지(Dirty Checking) 기억나죠?** 우아하지만, **수가 많아지면 독이 된다.**

```java
// "모든 회원의 활동점수를 100점씩 올려라"
List<Member> members = memberRepository.findAll();   // 1만 명을 전부 메모리로
for (Member m : members) {
    m.addActivityPoint(100);                         // 1만 번 변경 감지
}
// flush 시점에 UPDATE SQL이 1만 번 나간다
```

이런 **대량 일괄 수정**은 변경 감지로 풀면 안 된다. 이때는 `@Query` 로 **벌크 연산**을 직접 작성해 한 방에 처리한다.

```java
@Modifying
@Query("UPDATE Member m SET m.activityPoint = m.activityPoint + :amount")
int addActivityPointToAll(@Param("amount") int amount);
// → UPDATE 한 번으로 끝
```

여기 처음 보는 `@Modifying` 이 붙어있다. **그게 다음 절의 주제다 — 왜 이걸 굳이 따로 붙여줘야 하는지.**

### @Modifying — 변경 쿼리에만 붙이는 스위치

`@Query` 는 기본적으로 **조회(SELECT)** 라고 가정한다. 그래서 결과를 엔티티로 매핑해 돌려주려 한다(내부적으로 `getResultList()` 를 부른다).
그런데 우리가 적은 게 `UPDATE`/`DELETE` 라면 실행 방식 자체가 다르다 — 변경 쿼리는 `executeUpdate()` 로 실행하고, 결과로 **영향받은 행 수**를 돌려줘야 한다.

`@Modifying` 이 바로 그 스위치다. **"이 `@Query` 는 SELECT 가 아니라 UPDATE/DELETE 다. `executeUpdate()` 로 돌려라"** 라고 Spring Data JPA에 알려준다.

```java
// ❌ @Modifying 없음 → UPDATE 를 조회처럼 처리하려다 런타임 예외
@Query("UPDATE Member m SET m.activityPoint = m.activityPoint + :amount")
int addActivityPointToAll(@Param("amount") int amount);

// ✅ @Modifying 있음 → executeUpdate() 로 실행, 영향받은 행 수(int) 반환
@Modifying
@Query("UPDATE Member m SET m.activityPoint = m.activityPoint + :amount")
int addActivityPointToAll(@Param("amount") int amount);
```

#### 헷갈리지 말 것 — "UPDATE/DELETE면 무조건"이 아니다

흔한 오해가 **"UPDATE/DELETE 면 `@Modifying` 을 붙인다"** 이다. 정확한 규칙은 더 좁다.

> **`@Modifying` 은 "내가 `@Query` 로 UPDATE/DELETE 를 직접 작성했을 때"만 붙인다.**

트리거는 *쿼리의 종류*(UPDATE/DELETE)가 아니라 ***`@Query` 를 직접 적었는지 여부*** 다.
데이터를 바꾸는 다른 경로들은 `@Query` 를 안 쓰거나 Spring 이 알아서 처리하므로 `@Modifying` 이 필요 없다.

| 데이터를 바꾸는 방식 | `@Modifying`? | 이유 |
| --- | :---: | --- |
| `@Query("UPDATE/DELETE ...")` 직접 작성 (벌크) | ✅ **필요** | 내가 쓴 변경 쿼리. `executeUpdate()` 로 돌리라고 알려야 함 |
| `save()`, `delete()`, `deleteById()` (기본 제공) | ❌ 불필요 | Spring 이 만든 구현체가 알아서 처리 (`@Query` 가 아님) |
| 변경 감지 (조회 후 값만 변경) | ❌ 불필요 | **쿼리를 아예 안 씀** — flush 때 JPA 가 자동 UPDATE |
| 파생 삭제 메서드 `deleteByEmail(...)` | ❌ 불필요 | 메서드 이름의 `delete` 키워드를 Spring 이 인식해 처리 |

```java
// ✅ @Modifying 필요 — 내가 @Query 로 UPDATE 를 직접 씀
@Modifying
@Query("UPDATE Member m SET m.activityPoint = m.activityPoint + :amount")
int addActivityPointToAll(@Param("amount") int amount);

// ❌ @Modifying 불필요 — 파생 쿼리, Spring 이 delete 키워드를 인식
void deleteByEmail(String email);

// ❌ @Modifying 불필요 — 쿼리 자체가 없음 (변경 감지)
Member m = memberRepository.findById(id).orElseThrow();
m.changeName("홍길동");   // flush 시 자동 UPDATE
```

> **이어지는 함정:** `@Modifying` 으로 실행한 벌크 UPDATE/DELETE 는 **영속성 컨텍스트를 우회**해 DB 로 직행한다.
> 그래서 1차 캐시에 남아 있던 엔티티는 **옛날 값(stale)** 을 들고 있게 된다. 바로 위 [변경 감지의 맹점 — 대량 처리](#️-변경-감지의-맹점--대량-처리)에서 본 그 문제이며,
> `@Modifying(clearAutomatically = true)` 로 실행 후 캐시를 자동으로 비워 해결한다.

#### 플래그 두 개 — flushAutomatically / clearAutomatically

벌크 연산이 컨텍스트를 우회하면서 생기는 **앞뒤 동기화 문제**를 막아주는 옵션이다.

```java
@Modifying(flushAutomatically = true, clearAutomatically = true)
@Query("UPDATE Member m SET m.activityPoint = m.activityPoint + :amount")
int addActivityPointToAll(@Param("amount") int amount);
```

| 옵션 | 시점 | 막아주는 문제 |
| --- | --- | --- |
| `flushAutomatically = true` | 벌크 **실행 전** | 컨텍스트에 아직 flush 안 된 변경(dirty)이 있으면 DB에 먼저 반영하고 벌크 실행. 안 하면 벌크가 **옛날 DB 상태** 기준으로 돌아 어긋난다 |
| `clearAutomatically = true` | 벌크 **실행 후** | DB만 바뀌고 캐시는 stale → 캐시를 자동으로 비워, 이후 조회가 DB를 다시 읽게 한다 (= 우리가 손으로 한 `em.clear()` 의 자동화) |

> **⚠️ `clearAutomatically` 의 대가:** 컨텍스트를 **통째로 비우므로**, 같은 트랜잭션에서 들고 있던 **다른 엔티티까지 전부 준영속(detached)** 이 된다.
> 그래서 가장 견고한 패턴은 **벌크 연산을 별도 트랜잭션(`@Transactional(propagation = REQUIRES_NEW)`)으로 격리** + 플래그 ON 이다.
> 반대로 **벌크가 그 트랜잭션의 마지막 작업이고 이후 그 데이터를 다시 안 읽는다면** 컨텍스트는 곧 소멸하므로 플래그가 사실상 불필요하다.

## 6단계. LazyInitializationException — 프록시의 그림자

### 3주차에서 본 프록시, 기억하시죠?

3주차(12페이지)에서 `fetch = LAZY` 일 때 `member.dept` 자리에는 진짜 객체가 아니라
**프록시(가짜 객체)** 가 들어가고, **실제로 값을 꺼내는 순간** SQL이 나간다고 배웠다.
이번 주의 마지막 함정이 바로 그 프록시에서 나온다.

### 왜 터지나

```java
@Service
public class MemberService {

    @Transactional
    public Member findMember(Long id) {
        return memberRepository.findById(id).orElseThrow();
    }   // ← 여기서 트랜잭션 끝 → 영속성 컨텍스트 소멸 → member는 '준영속' 상태가 됨
}

// 컨트롤러 등 트랜잭션 밖에서:
Member member = memberService.findMember(1L);
member.getDept().getName();   // 💥 LazyInitializationException!
```

`dept` 는 아직 **로딩되지 않은 프록시**다. 진짜 값을 가져오려면 SQL을 날려야 하는데,
그 SQL을 날릴 **영속성 컨텍스트(=트랜잭션)가 이미 닫혀버린** 뒤라 가져올 방법이 없다.
그래서 `LazyInitializationException` 이 터진다.

> **1단계의 "영속 vs 준영속" 구분이 여기서 회수된다.**
> 프록시 초기화는 **영속 상태(트랜잭션 안)** 에서만 가능하다.

### 해결 방향 (지금은 개념만)

- **트랜잭션 안에서** 필요한 값을 미리 꺼내 둔다 (예: 서비스 안에서 `getDept().getName()` 호출).
- 조회 시점에 연관 엔티티를 **함께** 가져온다 → **Fetch Join / `@EntityGraph`** (다음 주, 양방향 매핑과 N+1을 다루며 본격적으로).

## 한 줄 요약

> 모든 마법(1차 캐시·쓰기 지연·**변경 감지**)은 **영속성 컨텍스트**에서 나오고,
> 그 수명은 **`@Transactional`** 이 정한다.
> Repository는 `JpaRepository` 상속만으로 기본 CRUD를 얻고,
> 조회 결과는 **`Optional` + `orElseThrow`** 로 안전하게 꺼낸다.
> 단순 조회는 **쿼리 메서드**, 복잡하면 **`@Query`(JPQL)** — 단, 문자열 쿼리의 오타는 **런타임**에 터진다.
> 그리고 트랜잭션 밖에서 LAZY 프록시를 건드리면 **`LazyInitializationException`** — 이건 다음 주 N+1·Fetch Join으로 이어진다.
