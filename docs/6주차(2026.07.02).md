## 0단계. 복습 — 5주차에서 Fetch Join 까지 왔다

5주차에서 확인한 것:

- **N+1** — 목록 1번 + 연관 N번. LAZY 프록시를 하나씩 깨우다 쿼리가 폭발한다.
- **Fetch Join** — 조회 쿼리에서 연관을 **JOIN 으로 함께 채워와** `1+N` → **1**.
- **`@EntityGraph`** — JPQL 없이 애너테이션으로 같은 효과.

이 셋의 공통점은 **"엔티티를 (프록시든 진짜든) 만들어서 다룬다"** 는 것이다. Fetch Join 은 그 엔티티의 연관을 미리 채워줄 뿐, **엔티티 자체는 여전히 영속 객체**다. 그래서 수정(변경 감지)이 되는 대신, **모든 컬럼을 싣고 영속성 컨텍스트가 관리**하는 비용을 치른다.

6주차의 첫 질문은 여기서 출발한다 — **"읽기만 할 화면인데도 굳이 엔티티를 만들어야 할까?"** 그 답이 1단계 **DTO 프로젝션**이다.

## 1단계. DTO 프로젝션 — 애초에 엔티티를 안 만든다

### 두 레벨 — 엔티티 변환 vs 쿼리 프로젝션

"DTO 를 쓴다" 는 말은 사실 **두 가지 다른 레벨**을 가리킨다. 이걸 구분해야 "언제 어느 걸 쓰나" 가 풀린다.

| | ① 엔티티 → DTO 변환 (앱 레벨) | ② DTO 프로젝션 (쿼리 레벨) |
| --- | --- | --- |
| 방법 | 엔티티를 가져온 뒤 자바에서 `MemberResponse.from(m)` | `SELECT new Dto(m.name, m.dept.deptName)` |
| DB 가 읽는 컬럼 | **전체** | **필요한 것만** |
| 목적 | 순환 차단·응답 모양 정리·계층 분리 | **조회 성능 최적화** |
| 엔티티 | 만든다(영속) | **안 만든다** |

> ①은 5주차 1단계의 무한 순환에서 이미 썼다(`MemberResponse.from()`). 엔티티는 그대로 두고 **응답 모양만** 바꾸는 것. ②는 한 발 더 나가 **DB 단에서 필요한 컬럼만** 뽑아, 엔티티·프록시를 **아예 안 만든다.** 이 단계의 주인공은 ②다.

### 쿼리 프로젝션 문법 — JPQL 생성자 표현식

먼저 받을 그릇(DTO)을 만든다. 필요한 값만 담는 **읽기 전용** 객체다.

```java
public record MemberDto(String name, String deptName) { }
```

그리고 JPQL 에서 `SELECT new` 로 **그 생성자에 값을 직접 채워** 가져온다.

```java
@Query("SELECT new com.example.spring.studyjpa.dto.MemberDto(m.name, m.dept.deptName) FROM Member m")
List<MemberDto> findAllDto();
```

```
-- 실행 SQL: 필요한 두 컬럼만, dept 는 조인으로
SELECT m.name, d.dept_name
FROM member m
JOIN department d ON m.department_id = d.id;
```

> [!Caution]
> **`new` 뒤에는 패키지까지 포함한 전체 경로(FQN)** 를 적어야 하고, **생성자의 인자 순서·타입이 정확히 일치**해야 한다. (그래서 컴파일 타임에 안 잡히고 런타임에 터지기 쉬운 게 이 방식의 단점 — 뒤의 QueryDSL `@QueryProjection` 이 이걸 보완한다.)

### 왜 N+1·프록시가 원천 차단되나

핵심은 **"엔티티를 안 만든다"** 는 데 있다.

- `m.dept.deptName` 은 **쿼리 시점에 JOIN** 으로 처리돼 **값(String)** 으로 바로 들어온다.
- 결과는 `Member`·`Department` 엔티티가 아니라 **`MemberDto` 라는 평범한 객체**다. **프록시가 없다.**
- 깨울 프록시가 없으니 **N+1 이 생길 여지 자체가 없다.** (Fetch Join 은 "N+1 을 해결" 하지만, DTO 프로젝션은 "N+1 이 **태어나지 않게**" 한다.)

```
Fetch Join : 프록시를 만들되 → 미리 채워서 N+1 을 막는다
DTO 프로젝션: 프록시를 아예 안 만든다 → N+1 이 생길 곳이 없다
```

### Fetch Join vs DTO — 무엇을 언제

이 단계의 심장. 둘은 경쟁이 아니라 **쓰는 자리가 다르다.**

| | Fetch Join | DTO 프로젝션 |
| --- | --- | --- |
| 가져오는 것 | **엔티티**(영속) | **그냥 객체**(비영속) |
| 컬럼 | 전체 | **필요한 것만** |
| 변경 감지 | ✅ 됨 | ❌ 안 됨 |
| N+1 | 해결함 | 애초에 안 생김 |
| 메모리/비용 | 무거움(영속성 컨텍스트 관리) | 가벼움 |
| 쓰는 곳 | **수정도 할 흐름** | **읽기 전용 화면(목록·리포트)** |

> **한 줄:** 값을 **바꿔서 저장할 거면 엔티티 + Fetch Join**, **화면에 뿌리기만 할 거면 DTO 프로젝션.**

### ⚠️ 트레이드오프 — DTO는 변경 감지가 안 된다

DTO 는 영속성 컨텍스트가 관리하는 객체가 아니다. 그래서 **값을 바꿔도 `flush` 때 UPDATE 가 나가지 않는다.** (당연하다 — 영속 객체가 아니니까.)

```java
MemberDto dto = repo.findAllDto().get(0);
// dto.name = ... 바꿔도 DB 는 그대로. dto 는 그냥 자바 객체일 뿐.
```

이게 단점이 아니라 **역할**이다. "읽기 전용" 이라는 의도를 타입으로 못박는 셈이다. 수정이 필요하면 엔티티를 쓰면 된다.

### 참고) 프로젝션 세 가지 방식

> [!Note]
> 같은 "필요한 컬럼만 뽑기" 를 세 가지로 쓸 수 있다. 깊게는 실무에서 골라 쓰면 되고, 여기선 존재만 안다.
>
> | 방식 | 예 | 특징 |
> | --- | --- | --- |
> | **JPQL 생성자 표현식** | `SELECT new ...MemberDto(m.name, m.dept.deptName)` | 표준. FQN·생성자 일치 필요(런타임 위험) |
> | **인터페이스 프로젝션** | `interface MemberView { String getName(); String getDeptName(); }` | 스프링 데이터가 구현 자동 생성. 가장 간단 |
> | **QueryDSL `@QueryProjection`** | `new QMemberDto(member.name, member.dept.deptName)` | **컴파일 타임에 검증** + 동적 쿼리에 강함 |

## 2단계. OSIV — 편함과 위험의 트레이드오프

### OSIV란?

**OSIV(Open Session In View)** = 요청이 **끝날 때까지** 영속성 컨텍스트(와 DB 커넥션)를 **살려두는** 설정이다. 스프링 부트 기본값은 **켜짐(`true`)** 이다.

```yaml
spring:
  jpa:
    open-in-view: true   # 스프링 부트 기본값
```

그래서 서비스 트랜잭션이 끝난 뒤 **컨트롤러·뷰에서 LAZY 프록시를 건드려도** 통로가 살아 있어 값을 채울 수 있다. → 4주차의 `LazyInitializationException` 이 **"안 생기는"** 이유가 바로 이것이다.

```
OSIV on : [요청 시작] ── 영속성 컨텍스트 ───────────── [요청 끝]
                          (트랜잭션 끝나도 컨텍스트는 살아있음 → 컨트롤러 LAZY OK)
```

### 켜기 vs 끄기

편함에는 대가가 있다.

| | OSIV **on** (기본) | OSIV **off** |
| --- | --- | --- |
| 컨트롤러/뷰에서 LAZY | ✅ 터지지 않음 | ❌ `LazyInitializationException` |
| DB 커넥션 | **요청 내내 점유** | 트랜잭션 끝나면 **바로 반납** |
| 장점 | 개발이 편함 | 커넥션 회전율↑ → 확장성 좋음 |
| 단점 | 트래픽 많으면 **커넥션 고갈·성능 저하** | LAZY 를 트랜잭션 안에서 **미리 처리**해야 함 |

> [!Caution]
> **OSIV on 의 진짜 비용은 "DB 커넥션을 요청 끝까지 붙잡는 것"** 이다. 트랜잭션이 끝나 더 이상 DB 가 필요 없어도, 뷰 렌더링까지 커넥션을 반납하지 않는다. 동시 요청이 많으면 커넥션 풀이 금방 마른다.

**실무 권장:** 트래픽 규모가 있는 서비스는 **OSIV off + 명시적 조회(Fetch Join / DTO)**. 컨트롤러가 LAZY 를 건드리지 않도록, **필요한 연관은 트랜잭션 안에서 미리** 당겨오거나 DTO 로 변환해 내보낸다.

### ⚠️ OSIV off 의 또 다른 함정 — merge 함정

> [!Caution]
> OSIV 를 끄면 서비스 트랜잭션이 끝나는 순간, 반환된 엔티티가 **준영속(detached)** 이 된다. (4주차에서 예고한 그 함정이 여기서 현실이 된다.)
>
> 이 준영속 엔티티를 컨트롤러에서 다시 `save()` 하면 — `save()` 는 준영속 엔티티에 대해 내부적으로 **`merge()`** 를 실행하는데, `merge()` 는 원본을 영속화하는 게 아니라 **복사본을 새로 만들어 반환**한다. 그래서 **반환값을 버리고 원본을 수정하면** 변경 감지가 동작하지 않는다.
>
> ```java
> Member detached = memberService.findMember(1L); // 트랜잭션 밖 → 준영속
>
> memberRepository.save(detached);   // ❌ 반환값 버림 — 원본은 여전히 준영속
> detached.changeName("새이름");      // 변경 감지 안 됨 → DB 반영 X
>
> Member managed = memberRepository.save(detached); // ✅ 반환값을 받아야
> managed.changeName("새이름");       // managed 가 영속 상태 → DB 반영 O
> ```
>
> **핵심:** OSIV off 를 선택했다면 **반환값을 DTO 로 변환하거나, `save()` 반환값을 반드시 받아서** 쓴다. 더 나은 정공법은 **수정 로직을 서비스(트랜잭션 안)에 두고, 컨트롤러는 DTO 만 주고받는** 것이다.

## 3단계. 선택 기준 — 언제 무엇을

지금까지의 도구(Fetch Join·`@EntityGraph`·DTO·OSIV)를 **상황별로** 정리하면 이렇다.

| 상황 | 권장 | 이유 |
| --- | --- | --- |
| 단건 + 연관 몇 개, **수정도 함** | Fetch Join / `@EntityGraph` | 엔티티 유지 → 변경 감지 가능 |
| **목록·리포트 (읽기 전용)** | DTO 프로젝션 | 프록시·N+1 원천 차단 + 필요한 컬럼만 |
| 컬렉션(1:N) + 페이징 | 루트만 페이징 + **batch fetch size** | 컬렉션 Fetch Join 페이징 함정 회피 (5주차 보충자료) |
| 전역 LAZY 편의 (작은 앱) | OSIV on | 편하지만 커넥션 비용 |
| 트래픽 큰 서비스 | **OSIV off + 명시적 조회** | 커넥션 빨리 반납 → 확장성 |

> **판단 순서:** ① 이 조회로 **수정까지** 하나? → 엔티티(+Fetch Join). ② **읽기만** 하나? → DTO. ③ 가져올 게 **컬렉션 + 페이징** 인가? → batch fetch size. ④ 그리고 **OSIV 는 끈 상태**를 기본으로 두고, 위 ①~③ 로 LAZY 를 트랜잭션 안에서 미리 해결한다.

## 한 줄 요약

> N+1 해결책은 **무엇을 언제** 쓰느냐로 갈린다.
> **수정도 할 흐름 → 엔티티 + Fetch Join**, **읽기 전용 → DTO 프로젝션**(프록시·N+1 원천 차단, 단 변경 감지 X).
> **OSIV** 는 켜면 편하지만 커넥션을 요청 내내 붙잡으니, 규모가 커지면 **끄고(off) 명시적 조회**로 — 대신 `merge` 함정을 조심한다.
> 정공법은 **LAZY 기본 + 필요할 때만 명시적으로 당겨오기**, 그리고 **읽기는 DTO 로 가볍게.**
